# 植物资产格式（vegetation asset format）v1

> 位置：`tools/jpov/tools/vegetation_tool_v2/`
> 状态：设计定稿（2026-10-20），实现见同目录 `proto/shape.proto` / `shape.h`。
>
> **文件格式（2026-10-26 约定）**：资产一律存**二进制 `.vegshape`**（本文 proto 的
> protobuf wire format）；文本 `.pbtxt` 只用于人工查看/diff，用 `gen/shape_convert` 互转
> （`pbtxt → vegshape → pbtxt` 逐字节可逆）。下面讲的是**字段语义**，与编码无关。

---

## 0. 一句话

**一棵植物 = 拓扑（`ShapeProto`） + 树皮材质 + 叶材质。三样各自独立，装配时合体。**

```
shape.pb  ─┐
bark/     ─┼─→ assemble ─→ tree.glb (+ resolved manifest)
leaf/     ─┘
```

- **拓扑**只描述几何：枝干折线、粗细、截面、叶卡的位置与朝向。**不含任何纹理信息。**
- **材质**只描述外观：贴图、网格划分、PBR 参数。
- 因此：同一份拓扑可以换 N 套树皮、换 N 套叶子；同一套材质可以套到不同拓扑上。

为什么用 protobuf 而不是 JSON：这个结构对约束的要求很高（单位、朝向、拓扑一致性、必填字段），
proto 自带 schema、默认值语义、向后兼容版本号，且**跨语言**（Blender 侧 Python、引擎侧 C++）。
JSON 靠约定，错了不报错；proto 错了编不过。

---

## 1. 全局约定（**硬编码，不进 schema**）

| 约定 | 值 |
|---|---|
| **单位** | **米（m）**；角度用弧度 |
| **上方向** | **+Y**（glTF 约定） |
| **截面** | **归一化**（半径的倍数，不是米）、逆时针、闭合不重复首尾、星形 |

**为什么不做成字段**：多一个 `units`/`up_axis` 字段就多一个能被填错的地方，而它们永远只有
一个正确值。写死在注释和校验里即可。

⚠️ **Blender 是 +Z up**，导出时必须转：`(x, y, z)_blender → (x, z, -y)_gltf`。
这和 `wind_bake` 里写风关节枢轴时踩过的坑是同一个（当时也是忘了转，枢轴比 mesh 差一个轴旋转）。

## 2. 枝干

### 2.1 数据

```
Branch {
  id, parent, level,
  samples: [ { position(x,y,z), radius, tilt, profile[] } ... ],   // 采样折线
  ring_count,
  seam_index
}
```

- **`samples` 是采样折线，不是贝塞尔控制点**。曲线形状已经在导出时烘进来了；
  下游只做线性插值，不需要实现贝塞尔求值。
- **`radius` 逐点给**，所以锥度、收细、领口过渡全都是数据，不是算法。
- **`parent = -1`** 表示根枝；其余指向父枝 `id`。要求 `parent` 出现在自身之前（无环、拓扑序）。
- **`tilt`**：截面绕切线的自转角（弧度）。正圆截面下不可见，非圆截面时它决定截面朝向。
- **`seam_index`** 放在 branch 级（不是 sample 级）：接缝沿枝必须稳定，否则纹理会沿枝拧转。

### 2.2 截面轮廓（**逐采样点**）

截面挂在**每一个采样点**上，不是全树一份。这样塑形噪音（越往上越扁、根部板根、局部鼓包）
就是纯数据，不需要任何算法。

**坐标定义（别含糊）**

| 项 | 定义 |
|---|---|
| **所在平面** | 过该采样点、**垂直于中心线切线 T** 的平面 |
| **原点** | 该采样点在中心线上的位置 C |
| **坐标轴** | x 沿 U，y 沿 V；(U, V, T) 是右手系，U 由平行传输得到 |
| **单位** | **半径的倍数（不是米）** |

```
世界坐标 = C + radius · ( x·U + y·V )
```

例：`(x=1, y=0)` = 「沿 U 方向、距中心线恰好 radius」的那个管壁点。

所以 **`radius` 只负责粗细，`profile` 只负责形状**，两者正交：

- 树干变粗 → 只改 `radius`
- 圆变板根/沟槽 → 只改 `profile`
- 逐点半径变化 → 锥度

**约定**：从 `+T` 方向看逆时针；闭合、首尾不重复；星形（任意方向只交一次）。

**留空 = 正圆**，点数由 `ring_count` 决定。绝大多数枝条是正圆，留空既不丢信息又省体积。

**一致性**：同一根枝上，非空 `profile` 的点数必须都等于该枝的环顶点数
（`ring_count` 显式值，或 profile 自身点数）。不一致会让相邻两圈接不上、三角化错位。

### 2.3 扫管（生成网格）

对第 `i` 个采样点，环上第 `j` 个顶点：

```
P(i, j) = C_i + r_i · R(tilt_i) · ( x_j·U_i + y_j·V_i )
```

- `U_i / V_i`：垂直于切线的横截面基，沿枝**平行传输**（避免管子自己拧）
- `(x_j, y_j)`：`CrossSection.points` 的第 j 个点，单位化（`r=1` 时就是轮廓本身）
- 圆截面 = 单位圆上取 `ring_count` 个点

**`ring_count` 逐枝可不同**：主干 16（看不出棱角），末梢枝 6–8（省面）。`0` = 用截面点数。

### 2.4 分叉

子枝的入口直接插进父枝体内（**不焊接**）。

- 好处：UV 可以在接口处连续推进（见 §3.3），不需要处理焊接后的共享顶点
- 代价：交界处有一圈硬接缝 → 用**领口过渡**盖掉（子枝根部半径从父枝半径沿 smoothstep 收细，
  过渡长度 = `junction_blend × 父半径`，这笔是渲染侧的几何处理，不进 `ShapeProto`）

## 3. UV（纹理怎么贴上去）

### 3.1 规则

```
u(i, j) = (从 seam 顶点沿第 i 点截面走到第 j 点的累计边长) × r_i / tile_i
v(i)    = (从根沿枝的累计中心线弧长) / (tile_i / uv_v_scale)
tile_i  = r_i × perimeter(第 i 点的单位截面)
uv_v_scale = 贴图宽 / 高        // 方形贴图 = 1；见 §3.2
```

> `perimeter` 用**真实多边形边长**累加，不是 `2πr`：低模环（8/12 边）的真实表面比理想圆短，
> 用 `2πr` 会把纹理横向多算约 14%。截面逐点可变时更是必须逐点算。

三条性质：

1. **长宽比精确**：u 和 v 都是真实弧长除以同一个 `tile_i`，同一根枝上纹理不会被拉伸。
2. **纹路沿枝生长方向**：v 就是生长方向，图片的 +Y 永远朝枝梢。
3. **任意粗细循环**：`tile_i` 跟着周长走，所以 4cm 的细枝也是"一圈一张图"——
   纹路自动变细（真实树皮也是这样），而不是只用到贴图 4% 的宽度。

> **不设下限**：`tile_i` 恒等于该采样点的周长。
> 一旦设下限（例如 `max(tile, 0.15m)`），细枝的 `u` 就只走到 `周长/0.15 < 1`，
> 接缝处贴图从 0.84 跳回 0 —— 那是**硬缝**，不是循环。要加下限只能改成"整数圈"，
> 而 `n ≥ 1` 时最小值还是 `tile = 周长`，等于没加。

**锥度的固有代价（要说清楚）**：`u` 是角向的（与半径无关），而世界宽度随半径缩小，
所以**相邻两圈之间那一个带**（不是整圈、更不是整根枝）会被映射成梯形，带内横向/纵向比例
偏离 1:1。量级只取决于**单段半径变化率**：

```
各向异性 ≈ (r_i − r_{i−1}) / (2·r_{i−1})      // 逐段，与总锥度无关
```

| 情况 | 每段 Δr/r | UV 偏差（实测） |
|---|---|---|
| 半径恒定 | 0 | 0（只受多边形离散影响 <1%） |
| 总锥度 5%（6 采样） | ~0.45% | < 3%（实测 ~0.2%） |
| 总锥度 3×（0.15→0.05，5 段） | ~24.6% | ~15% |

> 注意别误读成「总锥度 3× → 偏差 200%」。整根枝是"每圈各自归一化"，所以圈与圈之间**没有累积**；
> 只有某一小段里半径突变才会在那一带看出拉伸。采样密（实际导出 `per_seg=16`）时一条正常锥度枝
> 每段 Δr/r 远小于 1%，肉眼不可见。
> 想彻底消掉，只能放弃"一圈一张图"（改成 u = 真实米数 / 1m），代价是细枝只用到贴图一角、
> 且接缝不再闭合。当前选择：**保接缝 + 保细枝铺满，接受锥度段的局部轻微收缩**。
>
> 若某资产确实出现「一段之内半径砍半」，正确做法是**在导出侧补采样点**
> （`|r_i/r_{i−1} − 1| > 2~3%` 就线性插一个点），不是改 UV 规则。

### 3.2 贴图长宽比（非方图必须补偿）

`tile` 在 u、v 上是同一个，前提是**贴图本身是正方形**（1m² 图 = 一圈 × 一圈）。
真实素材经常不是：ambientCG 的 `Bark001` 是 **512×1024（1:2）**。

不补偿会怎样：图片被硬压进一个方形 UV 域 —— 花纹在世界空间横向拉宽 2×、凸起被压扁，
法线贴图的细节也跟着糊（观感是"平"）。纹素不再是方的，§3.1 的「长宽比精确」也就不成立了。

补偿就一条：

```
uv_v_scale = 贴图宽 / 高          // 512x1024 → 0.5
v_new      = v × uv_v_scale
```

等价于把每段的 `tile` 除以 `uv_v_scale`。这样：

- u 方向：512 px 铺满一圈 → 纹素宽 = `tile/512`
- v 方向：1024 px 铺 `tile/0.5 = 2·tile` 米 → 纹素高 = `2·tile/1024 = tile/512` ✓ 方形

接口：`SweepOptions::uv_v_scale`（默认 1.0，必须 > 0）。**装配方知道材质，由它传**——
拓扑不含纹理信息（§1），所以这个值不进 `ShapeProto`。父子的接续项 `gap/tile_parent`
必须与枝内累计项用同一个 `uv_v_scale` 缩放，否则接口处会错行（`sweep.cc` 里两处一起乘）。

### 3.3 父子接口的 V 连续

子枝入口的 v 不是从 0 开始，而是：

```
v_child(0) = v_parent(出口) + |P_child(0) − P_parent(出口)| × uv_v_scale / tile_parent
```

超过 1 取模（贴图可平铺）。**这一步是"整棵树纹理不断"的关键**：否则每根枝都从贴图第 0 行开始，
接口处会出现一条明显的横向重复线。

子枝入口环的第 0 点（seam）方向 = 父枝出口环第 0 点方向**投影到子枝横截面上**，
保证接口处 U 相位连续，不会有纹路拧转。

### 3.4 树皮材质（文件约定 + 法线强度）

一个树皮材质 = 一个目录，固定三个文件（`fetch_textures.sh` 下的 ambientCG JPG 用
`make_bark_material.sh` 转换即得）：

| 文件 | 来源 | 说明 |
|---|---|---|
| `albedo.png` | `*_Color.jpg` | baseColor，**必须无缝可平铺**（u 方向要 wrap） |
| `normal.png` | `*_NormalGL.jpg` | **OpenGL 约定**（绿 = +v）。引擎侧 `B = cross(N, T)`，与 +v 同向 |
| `roughness.png` | `*_Roughness.jpg` | 灰度 → 采 `.r` |

- 贴图 wrap = **REPEAT**（u 每圈归零、v 沿枝累加都会超 1）。用 CLAMP 会把整张图拉成边缘色。
- 法线贴图要求 mesh 带 `kTangent`（扫管会生成，切线 = ∂P/∂u）。
- **法线强度默认 1.5**（viewer 的 `--normal-scale` / 面板滑条，范围 0~3）。A/B 实测：
  1.0 偏平（天空 ambient 占比高，N·L 对比被冲淡）、3.0 发塑料、1.5 最自然。
  这是**呈现参数，不进资产**：换光照/换引擎时该重调。
- mipmap 必须开：树干是透视大平面，不开会摩尔纹。注意 mip 平均会让法线细节随距离自然变平
  （本图平均斜率 L0 0.39 → L2 0.15），这是物理正确行为，不要试图用 mip 层"补强"。

## 4. 叶卡

### 4.1 数据

```
LeafCard {
  anchor(x,y,z),      // 叶-枝连接点（**必须在枝条上**；见下面的合同）
  up(x,y,z),          // 卡片长轴，从根指向梢
  normal(x,y,z),      // 卡面法线
  height,             // 沿 up 的长度（米）
  width,              // 沿 right(=up×normal) 的宽度（米）
  type,               // 叶卡类型编号（int，从 0 开始）
  branch, s           // 溯源：挂在哪根枝的哪个参数位置（渲染不依赖）
}

LeafType {
  type, description, anchor_mode,
  bend { along, across, crease }   // 叶面弯曲（见 §4.5；省略 = 平面卡）
}
```


- **`anchor` 是「叶子与枝条的连接点」，必须落在所属枝条上**（合同，不是提示）：
  到 `branch` 那根枝中心线的距离 ≤ 该处 `radius + 1cm`（叶柄允许插进管壁，但不许悬空）。
  `Validate` 强制这一条。
  - **反例（历史 bug，2026-10-22）**：导出曾把 anchor 写成「根边中点 = 卡片中心 − up·h/2」，
    442 张卡全部偏出枝条 12~18cm。结果真正压在枝上的是**卡片中心**，
    4 种 `anchor_mode` 怎么选都贴不上枝 —— 素材画得再准也没用。
- **`anchor + anchor_mode` 唯一推导 UV**：格子里的 `(au, av)` 那一点贴到 `anchor`，
  卡片沿 `+up` 长、沿 `right(=up×normal)` 变宽：
  ```
  面片(u,v) = anchor + right·(u − au)·width + up·(v − av)·height + normal·z(u,v)   // z 见 §4.5
  ```
  引擎**不做任何补偿性偏移**：素材根部画在 `(au, av)`，逻辑就对得上。
- **anchor + up + normal** 三者唯一确定卡片姿态。只有 `up` 不够（卡面还能绕长轴自转）。
- **`anchor_mode`**（每类一份）：**只描述「根部落在格子的哪个位置」**，卡片永远沿 `up` 从根长到梢。
  - `bottom_left` / `bottom_center` / `bottom_right`：根部在下边 —— 叶、叶簇（叶簇卡常偏左下/右下）
  - `top_center`：根部在上边 —— 柔荑花序、垂花（根在上，往下垂）

  > 没有「根部在图片正中央」这种对齐方式：造图时没人会故意把根画在正中，
  > 它对用户是纯负担（早期草案里的 `center` 已删除，Validate 会直接拒绝）。

  **造图 checklist（唯一对照表，填错就是「叶子整体偏半张卡」）**：

  | 素材里根的画法（格内归一化） | 必须写 |
  |---|---|
  | 左下角 `(0, 0)` | `bottom_left` |
  | 底边中点 `(0.5, 0)` | `bottom_center` |
  | 右下角 `(1, 0)` | `bottom_right` |
  | 顶边中点 `(0.5, 1)` | `top_center`（垂花/花序） |

  入库样例：`assets/leaf/willow_leaf.png` 根在 `(0.07, 0.95)` → `bottom_left`；
  `assets/leaf/willow_leaf_flip.png`（左右翻转版）根在右下 → `bottom_right`。
- **`description`**：自然语言（"柳树主冠层叶簇，细长披针形 15×25cm，梢部下垂"）。给人和
  agent 看的；也用于将来做类型匹配。
- **`type` 为什么要分类**：一棵树可以有**内容完全不同**的多类卡——桑树的异形叶、柳树的
  柔荑花序、枯叶、花果。它们用不同 atlas、不同尺寸、不同数量。

### 4.2 宽度：**存进 shape**（装配时算好，运行时不猜）

```
width = height × (cell_width / cell_height)     // 装配时算，写进 LeafCard.width
```

- **anchor + up + normal + height + width（+ 所属 type 的 `bend`）唯一确定卡片面片**，
  引擎直接按这几个量铺面，不做任何"拿材质比例反推"的隐式行为（否则同一个 shape 换材质就变形状，
  无法复现）。`bend` 全 0 时就是平面 quad，见 §4.5。
- `width` 必须 > 0，`Validate` 会拒绝 0/负值。
- 贴图与 quad 的比例对不上时，呈现是**拉伸**的 —— 这是可见的、可修的：改 shape 的 width，
  或者改 atlas 格子比例后重新装配。引擎**绝不**为了凑形状去偷偷拉伸纹理。
- 曾有一个 `preferred_aspect`（"一型多 atlas 时挑哪套"的期望宽高比），2026-10-22 **删除**：
  装配层从未实现，全仓库没有消费方，留着只会让文档和导出脚本假装具备该能力。
  proto 里 `reserved 4`，编号不复用。真要实现"挑 atlas"时，按当时的真实需求重新设计字段。

（`cell_*` 指的是 atlas **格子**的尺寸，不是整张图的尺寸：`imgW/cols : imgH/rows`。）

### 4.2.1 debug 视图的角标（红/黄/蓝）

shape viewer 在「叶卡贴图关掉」时，会把每张卡画成 **绿卡 + 三个角标**（四色统一显示/隐藏）：

- **绿 = 整张 quad 的空间覆盖**（2cm 厚的盒子，只为看得见，不代表卡片有厚度）
- **红 = uv(0,0)、黄 = uv(1,1)、蓝 = uv(0,1)**：各是该角 **1/8 大小、3cm 厚** 的小盒子，
  角点与 quad 角点重合

四者共用同一套 pivot 与同一个 `width`，所以永远对齐。角标直接回答
"这张卡到底贴在哪、素材四角往哪对"；绿卡回答"它覆盖多大一块空间"。

### 4.3 叶材质的约定（写进物料规范，不进 `ShapeProto`）

1. **atlas 是 cols × rows 的网格**，一格 = 一张卡
2. **格子里，根部必须画在 `anchor_mode` 指定的位置**（叶/叶簇在下边，花序在上边）——
   与 §4.1 的四个取值一一对应；卡片 pivot 就落在那里
3. **内容必须撑满格子的宽度方向**（上下可以留白）。因为 `width` 由格子比例推导，
   左右留白会让叶子视觉上变胖
4. 一型将来可以绑多个 atlas 变体（**装配层尚未实现**）；真做的时候再决定按什么挑，
   现在没有 `preferred_aspect` 这类字段了（见 §4.1 的删除说明）
5. **黑底素材**（例如手绘/照片抠图）可以按「近乎黑 = 透明」自动转 alpha：先按
   `max(r,g,b)` 做软阈值，再按覆盖率反解颜色（`C = C_obs / α`，否则边缘一圈发黑）。
6. 叶卡的 alpha 是 cutout，且会被 mip 缩小 → **必须用覆盖率保持的 mip 链**
   （`TextureOptions::alpha_coverage`，cutoff 与材质 `alpha_cutoff` 一致），
   否则远处叶片变稀、只剩一根根细线。
7. **手性（左右镜像）必须拆成两个 leaf type**：Blender 里叶卡的 UV 可能是镜像的
   （实测 weeping_willow 预设约 48.7% 的卡是镜像）。一种 leaf type 只对应一种对齐方式，
   所以导出时按 UV 手性拆成 `type 0`（未镜像）与 `type 1`（镜像），
   由用户给 type 1 提供一张**左右翻转**后的素材；引擎不做运行时镜像。
8. 叶面细节可以吃「轮廓 alpha + 照片明暗 luma」生成的法线贴图（emboss）管叶脉/倒角；
   整张叶子的**弯曲**用 `LeafType.bend` 的真实几何（见 §4.5），不靠改法线去假装 ——
   「顶点法线球面化」那类做法只改法线不改几何，烘焙出来的 glb 与预览对不上。

## 4.4 整份 shape 的 `description`（万用提示词）

顶层还有一个 `description`，用途是**备注这份资产本身**：

- AI 生成这份 shape 时，说明「每种 leaf type 希望配什么素材」
- 或者「哪些素材风格接近、可以互换」
- 或者季节性/地域/风格备注

```jsonc
"description": "柳树，垂枝。leaf_type 0（冠层叶簇）适合 leafset_A / leafset_C，
                两者色系接近可互换；leaf_type 1（柔荑花序）只在春季出现，配 catkin_spring。"
```

**它永不参与逻辑判断**，只是给人 / agent / 下游工具读的上下文。可以为空。

### 4.5 叶面弯曲：叶子是**曲面**，不是平面 quad

`LeafType.bend` 三个系数，单位都是「这张卡的高度的倍数」（12 cm 的叶子写 0.15 = 1.8 cm）。

**先定义卡片自己的坐标**（不需要参考别处）：

- `u ∈ [0,1]`：宽度方向，0 = 左缘、1 = 右缘（世界方向 `right`）。
- `v ∈ [0,1]`：长度方向，0 = 叶柄、1 = 叶尖（世界方向 `up`）。
- **中脉线**：从叶柄指向格子中心的直线。它通常**不是** `v` 轴 —— 素材里的叶子多是斜着画的
  （叶柄在角上、叶尖在对角），中脉就是那条对角线；`jpov_leaf_card` 会把叶柄转到
  「从锚点角指向格内」，正是为了让这条线成立。
- `s`：「离中脉多远」。中脉线上 `s = 0`，最远的叶缘处 `|s| = 1`。
- `t`：「沿叶长走了多少」。叶柄处 `t = 0`，叶尖处 `t = 1`。

`s`、`t` 都按格子里实际能到达的最大值归一化，所以取值恒在 0~1，与卡的大小无关。

位移沿卡面法线 `normal` 方向（正 = 朝 `normal` 一侧凸起）：

```
z = height · ( along·t² + across·s² + crease·中脉脊(s) )
中脉脊(s) = sqrt(s² + 0.25²) − 0.25      // 中脉处为 0、往两侧增大；圆角，不是硬棱
面片(u,v) = anchor + right·((u−au)·width) + up·((v−av)·height) + normal·z
```

| 系数 | 在树上看到的效果 | 典型值（12cm 的卡） |
|---|---|---|
| `along` | 叶尖相对叶柄抬起（正）/ 垂下（负） | −0.2 ~ +0.15 ⇒ 叶尖差 2.4cm |
| `across` | 两侧叶缘朝 `normal` 卷起（正）= 叶面成浅杯；负 = 两缘往下翻 | 0.08 ~ 0.2 |
| `crease` | 中脉比两侧高（正）= 叶子像被沿中脉折过；负 = 一道浅沟 | 0.1 ~ 0.2 |

**为什么存参数、不存顶点**：三个数唯一确定一张任意精细的光滑曲面。顶点位置按上式精确求值，
法线由同式的解析偏导给出（不是把面法线平均、也不是有限差分），所以细分多密只影响轮廓、
不影响光照 —— 不会出现低模那种一块块折线。存三个数比存几万个顶点更小、也更精确。

**消费方可以依赖的三条性质**：

1. 叶柄处（`t = 0`）位移恒为 0 ⇒ 弯曲不会把叶子从枝条上带走，`anchor` 合同不受影响；
2. 离中脉的距离左右对称 ⇒ 镜像出来的卡（type 1）不用把系数取反；
3. 三个系数全 0 = 平板 ⇒ 与没有这个字段的旧资产逐字节一致。

**形状只由资产决定**：查看器/烘焙器按资产里的系数建网格并显示，但不提供「运行时改弯曲」的
滑条或命令行覆盖 —— 那样预览和最终资产会变成两套真相。想看别的形状，改配置重新生成。

### 4.6 枝条噪声：参数在生成配置里，资产里只有结果

主干和枝条的「不规整」（长短粗细不一致、中段弓出去、从上看左右扭）在这份格式里**没有参数字段**。
生成阶段算完就把结果烘进几何，下游只读结果：

| 字段 | 里面已经是噪声之后的东西 |
|---|---|
| `Branch.samples[i].position` | 已经弯过的中心线位置 |
| `Branch.samples[i].radius` | 该点的半径，已经乘过尺寸抖动 |
| `Branch.samples[i].profile` | 该点的截面形状（归一化点），将来承载截面噪声的结果 |

参数写在生成配置里（`generate.proto` 的 `ShapeNoise`：按枝级给的 `size_jitter` /
`bend_longitudinal` / `bend_lateral`），**不进资产、也不进查看器面板**。理由和叶子位置烘死的理由一样：
资产要能自解释，下游不能依赖某份配置还在手边；而查看器是看资产的地方，不是调生成参数的地方。

## 5. 装配流程

```
1. 读 ShapeProto → 校验（§6）
2. 逐枝扫管：截面 profile + 逐点半径 + 平行传输基 → 顶点/法线/三角形
3. 生成 UV：§3 的规则（含父子 V 连续、U 相位继承、非方贴图的 uv_v_scale）
4. 分叉领口：子枝根部按父半径 smoothstep 收细（渲染侧几何处理）
5. 叶卡：anchor/up/normal/height/width → 四边形（width 在装配时 = height × 格子宽/高，写进资产）；UV = atlas 格子四角
6. 材质：树皮接 albedo/normal/roughness；叶子接 atlas + alpha cutout + 双面
7. 输出：GLB + **resolved manifest**（记录每类卡实际用的 atlas、算出的 width）
```

`resolved manifest` 是必须的：`width` 依赖贴图，同一份拓扑换 atlas 会变宽 → 必须能回答
"昨天和今天生成的树为什么不一样"。

---

## 6. 校验（`Validate`）

装配前必须全过，任何一条不过就报错，不做兜底：

| 检查 | 理由 |
|---|---|
| `version != 0` | 版本必须显式给出（单位/上方向是硬编码约定，没有字段可校验） |
| 至少一根枝；恰好一根 `parent == -1` | 拓扑合法性 |
| `parent < id`，无环 | 拓扑序 |
| 每根枝 `samples.size() >= 2` | 不能扫出一条线 |
| 所有 `radius > 0` | 零半径=退化环 |
| 每枝能确定环顶点数（`ring_count > 0` 或存在非空 profile） | 否则无法扫管 |
| 非空 profile：点数 ≥ 3、等于环顶点数、逆时针星形、周长 > 0 | 截面合法且逐圈一致 |
| `seam_index < 环顶点数` | UV 接缝 |
| 每个 `leaf_type`：`anchor_mode` ∈ 4 个合法值 | 没有第五种对齐 |
| 每个 `leaf_type`：`|bend.along/across/crease| <= 1` | 系数是卡的 `height` 倍数；弯过自己一整张卡时位置/法线都没有意义 |
| 每张卡 `|up| ≈ 1`、`|normal| ≈ 1`、`up·normal ≈ 0` | 姿态合法 |
| 每张卡 `height > 0`、**`width > 0`**、`type` 在 `leaf_types` 里 | 引用完整、尺寸可铺面 |
| 卡片的 `branch` 存在，`s ∈ [0,1]` | 溯源完整 |
| **卡片的 `anchor` 落在所属枝条上**（到中心线 ≤ 该处 `radius + 1cm`） | `anchor` 的语义是叶-枝连接点；离枝则 UV 锚点落在卡片中间，素材怎么画都贴不上 |

---

## 7. 验收（视觉 + 数值，缺一不可）

**箭头测试图**（任意「带方向」的棋盘/箭头图：8×8 格、箭头朝上、有格线；
仓库里没有预置这张图，用导出的 UV 调试图或自己画一张）贴到树干上：

1. **所有枝条**的箭头都顺着枝走（主干朝上，斜枝朝斜上）
2. **格子是方的**（长宽比正确）
3. **树根左右密度一致**（u 沿截面是真实弧长，不是角度×半径的近似）
4. **接口处没有横向重复线**（父子 V 连续生效）

数值判据（从导出的 GLB 直接算）：

| 指标 | 期望 |
|---|---|
| `dv/dy`（主干预） | ±1.0，残差 std < 0.05 |
| 面片 uv/3d 面积比 | 中位数 1.0 ± 0.1 |
| 每类卡 `width/height` | 与 atlas 格子比例一致（误差 0） |

## 8. 版本与兼容

- `version = 1`。**加字段**不改版本（proto 天然向后兼容）；**改语义/单位**必须升版本。
- **2026-10-22 的 `anchor` 语义修正**（字段没变，数字含义变了）：早期导出把 anchor 写成
  「根边中点 = 卡片中心 − up·h/2」，导致 anchor 离枝 h/2（柳树 442 张卡偏 12~18cm），
  4 种 `anchor_mode` 怎么选都贴不上枝。现在 anchor 必须是**枝条上的叶-枝连接点**，
  `Validate` 强制；**旧导出资产会被直接拒绝**（不会静默错着渲染），需要重新导出。
  之所以没升 `version`：序列化布局没变，且旧数据会被新校验挡住，不存在"读进来悄悄走错路"的风险。
- 删除字段用 `reserved`，不复用编号。
- `description` 之类的自由文本永远不参与逻辑判断。
