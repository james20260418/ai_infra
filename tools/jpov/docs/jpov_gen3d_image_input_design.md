# JPOV gen3d 按图出模（image-driven generation）设计

> 本文记录 2026-09-18 与 Danis 的可行性讨论 + 结论，作为「按图出模」链路的落地依据。
> 覆盖两件事：
> **① 静态物体 / 人体的按图出模**（单图 + 四视图，本次 PR 做）；
> **② 在四视图出模基础上，把衣物"贴合到人模"的链路**（下一阶段，本文给出规划与边界）。
>
> 关联：`docs/jpov_gen3d_design.md`（文本→静态 PBR）、`docs/jpov_clothes_rig_design.md`
> （衣物绑骨 = weight transfer）、`gen3d/static/README.md`（工具使用说明）。

## 0. 起点：一个必须纠正的误解

`docs/jpov_clothes_rig_design.md` §2.2 铁律 A 原本写的措辞是
「Tripo **参考生成法** 贴着指定人体生成」，含义含糊，容易被读成
"给 Tripo 一个 **ref mesh**，让它基于这个 mesh 生成"。

**2026-09-18 核实 Tripo 官方 API：这个能力不存在。**

- Tripo 的 3D 生成端点**只接受三种输入**：文本 / 单图 / 多视图（2~4 张图）。
- **没有任何端点接受 3D 模型（mesh）作为"生成的参考条件"。**
- `POST /v3/models/import` 名字有误导性：它只是把外部 GLB/FBX/OBJ 传进 Tripo 平台
  **以便做后处理**（贴图/转换/重拓扑/绑骨/分割），**不能反过来驱动生成**。
- 佐证：Tripo 官方博客（2026-07-21）宣布与 **METATAILOR** 合作，由对方负责把
  Tripo 生成的衣物 **fit 到不同体型/骨骼的角色上**。即 Tripo 自己也认为
  「生成衣物」与「把衣物贴合到角色」是**两件事**，后者他们不做。

**正确表述**：所谓"参考生成"只能落地为
**「把参考渲染成图 → 用图的 endpoint 生成」**。mesh 传不进去，**图才能传**。

## 1. Tripo 能力矩阵（2026-09-18 核实）

### 1.1 生成类端点（输入只有 text / image / multiview）

| 端点 | 输入 | 说明 |
|---|---|---|
| `POST /v3/generation/text-to-model` | 文本 | 现有 `gen3d/static` 走的就是这条 |
| `POST /v3/generation/image-to-model` | **单图** | 支持 `file_token` / 公开 URL / 图像任务的 task_id |
| `POST /v3/generation/multiview-to-model` | **2~4 图** | 顺序 `[front, left, back, right]`，front 必填 |
| `POST /v3/generation/image-to-gaussian-splat` | 单图 | 高斯泼溅（本项目不用） |

### 1.2 图像类端点（本次要用）

| 端点 | 说明 | 价格 |
|---|---|---|
| `POST /v3/generation/text-to-image` | 文生图 | 5 credits |
| `POST /v3/generation/image-to-image` | 图生图（`input` + `inputs[]` 多参考图） | 5~10 credits |
| `POST /v3/generation/image-to-multiview` | 单图 → front/left/back/right 四视图 | 10 credits |
| `POST /v3/generation/edit-multiview` | 编辑四视图中的某一视图 | 5 credits/张 |

### 1.3 上传

| 端点 | 说明 |
|---|---|
| `POST /v3/files` | `multipart/form-data` 上传，返回 `file_token`（`file_xxx`）。图 ≤20MB（JPEG/PNG/WebP），模型 ≤150MB |

即：**本地图片 → `POST /v3/files` 拿 token → 传给生成端点。**

### 1.4 价格（官方 `developers.tripo3d.ai/en/pricing`，1 credit = $0.01）

| 任务 | 无贴图 | 标准贴图 |
|---|---|---|
| Text to 3D | 10 | 20 |
| **Image to 3D** | **20** | **30** |
| **Multiview to 3D** | **20** | **30** |

加价项：HD 贴图 +10 / 8K +20 / HD 几何 +20 / Quad +5 / Smart Low-poly +10 / Generate Parts +20。
动画：Rig Check 免费 / Auto Rig 25 / Retarget 10·动作。

> ⚠️ 第三方转售商（3DAIStudio 等）报价约为官方 **2 倍**，勿采用。

**单件成本估算**：衣物 = 图生多视图 10 + 多视图出模 30 ≈ **40 credits ≈ $0.40**。

## 2. 第一组：静态物体 / 人体的按图出模（本次 PR）

### 2.1 目标

在现有「文本 → 3D」基础上，打通 **「图 → 3D」**，覆盖单图与四视图两种输入。
静态物体与人体共用同一条链路（人体是"带特定约束的物体"，只是后续会接 rig）。

### 2.2 为什么值得做

1. **可控性**：文本靠 prompt 描述，AI 自由发挥（已知案例：`male_rig_test1.glb` 被
   Tripo 生成了冷灰蓝肤色，须在 prompt 里硬写 `warm skin tone` 才能纠正）。
   给参考图则肤色/体型/风格可控得多。
2. **是第二组的地基**：衣物贴合链路完全建立在"按图出模"之上，不打通则无从谈起。

### 2.3 本地格式审查（**强制，避免浪费 credit**）

**动机**：Tripo 只在"任务被受理"后才计费，但**格式不合规的图会被直接拒/生成垃圾，
等于白烧 credit**。且图像上传本身有硬性格式/尺寸限制。

因此在**本地、提交前**做审查，不通过的**直接拒绝，不发 HTTP**：

| 检查项 | 规则 | 依据 |
|---|---|---|
| 文件存在 / 可读 | 必须 | — |
| 扩展名 / magic bytes | `.png` / `.jpg` / `.jpeg` / `.webp` | Tripo 支持 JPEG/PNG/WebP |
| 文件大小 | ≤ 20 MB | 官方硬限制 |
| 分辨率 | 每边 ≥ 256 px | 官方推荐最小值（multiview 文档明示） |
| 宽高比 | 建议接近 1:1（四视图必须） | 见 §2.5 |

**PNG 特殊检查**：**alpha 通道**。详见 §3.3 —— 需在提交前判定图片是否带
非平凡 alpha，因为 Tripo 对 alpha 的处理方式未知（可能自动合成到背景色）。

> 采用**宽松策略**（校验硬性规则，不校验"好不好看"）。审查只截断明显浪费
> credit 的情况（不存在/超大/太小/格式不支持），不做美学判断。

### 2.4 接口设计（供应商无关原则的延续）

现有 `Gen3dConfig` 只表达"从文本生成"。按图出模需要**输入方式可切换**。设计：

```cpp
// 生成输入方式（互斥，语义上等价于"用户手里有什么"）。
enum class Gen3dInputMode {
    kText,        // 文本 prompt（现有路径）
    kSingleImage, // 单张参考图 → image-to-model
    kMultiview,   // 2~4 张参考图 → multiview-to-model
};
```

`Gen3dConfig` 增补：
- `Gen3dInputMode input_mode = Gen3dInputMode::kText;`
- `std::vector<std::string> input_image_paths;` — **由调用方声明路径**（工具不做隐式发现）

**图像路径由调用方显式声明**（本次交付要求）：不自动扫目录、不猜文件名。

四视图模式下，路径顺序即视图顺序 `[front, left, back, right]`；
允许少于 4 张（Tripo 允许 2~4），但 **front 必须有**。

### 2.5 工具使用说明要写清的"图片要求"

（将写入 `gen3d/static/README.md`，供找图的人直接照做）

- **单图**：主体清晰、背景干净、光照均匀；建议 ≥512×512；不要有明显透视畸变。
- **四视图**：**正面 / 左 / 背 / 右**，顺序严格；至少 2 张（正面必需）。
- **四视图的强约束（决定成败）**：
  1. **同一物体、同一光照条件**（官方原话）；
  2. **严格同一尺度、同一构图** —— 4 张图里主体的大小与位置应大致对应；
  3. 建议**裁成正方形**，主体居中；
  4. 分辨率一致。
- **手绘/拍照的额外提醒**（见 §3.4）：透视畸变与光照不均会显著劣化重建。

## 3. 第二组：衣物贴合到人模（下一阶段，本文只规划）

### 3.1 核心思路

> **提供者交付的不是衣物 mesh，而是一组「人穿着这件衣服」的参考图。**
> Tripo 吃这组图生成衣物 mesh，**位置与包裹关系在生成阶段就烘进几何里**。

这跟"先生成一件独立衣服、再想办法套上去"是两条完全不同的路。
我们要的是前者：**用参考图把贴合关系"画进去"**。

### 3.2 链路

```
T-pose 人体（已 rig，mixamorig 23 骨）
   ↓ jpov_model_viewer 渲 4 个正交视角 → 底稿
4 张「人体基准图」
   ↓ 提供者在图上画出衣物（形状 + 包裹关系）
4 张「穿着衣物的参考图」
   ↓ POST /v3/files 上传
   ↓ POST /v3/generation/multiview-to-model
衣物 GLB  ← 形状已贴合 T-pose 人体；位置/尺度随机；无骨骼无权重
   ↓ model_editor：只做平移 + 缩放，对齐到 T-pose 人体
对齐后的衣物
   ↓ （第三组）weight transfer 绑骨
可动画衣物
```

### 3.3 🔴 关键认知：四视图**给不出"位置"**

Danis 的质疑（2026-09-18）：「4 视图真的能把位置摆对嘛？我怀疑它顶多把形状摆对，
然后对齐资产还得靠 model_editor」——**这个判断成立，且应更严格**：

1. **multiview 重建出的是"物体自身的坐标系"**：Tripo 把 4 张图当成一个
   **独立物体**的多角度照片，重建出该物体自身的局部坐标。它**不知道**
   世界上还存在一具 T-pose 人体。
2. **图像里没有空间锚点**：multiview 端点接收的是**像素**，不是相机参数。
   它必须**猜**每张图的角度、距离、FOV。我们渲染时能做到精确正交 4 视角，
   但**这些元数据传不过去**（API 无相机内参/外参字段）。
3. **尺度是猜的**：`auto_size` 只决定"是否按真实世界米制"，不决定"对齐你的骨架"。
   两件衣物分别生成，尺寸会有偏差；同一件重生成一次又不同（除非钉 `model_seed`，
   而那也只保证同输入可复现，不保证跨资产对齐）。

**因此第二组的真实交付物是**：

> **一件「形状和包裹关系正确、但位置与尺度随机」的衣物 mesh。**

这不是"直接能穿"，而是**"已经解决了最难的部分：拓扑正确、贴身不穿模的几何形状"**。

### 3.4 因此：位置交给 model_editor（已有工具）

```
Tripo multiview         → 衣物几何（贴合形状已烘进去）
        ↓
model_editor（已有）    → 平移/缩放/对齐到 T-pose 人体
        ↓
（第三组）weight transfer → 绑骨
```

**形状与位置解耦之后，每一段都变得可独立验证、可独立重做**：

- Tripo 段失败 → 重生成，不影响已摆好的东西
- 摆位失败 → 只重摆，不重生成（省 credits）
- 且**摆位本就是 model_editor 的职责**（`interface/mesh_transform.h`
  + `jpov_gltf_saver` 已有"把放置烘进 CPU 资产并存自洽 glb"的能力）

**结论**：第二组的「让提供者把衣服形状**和位置**画对」应删掉"位置"那半句。
提供者只负责**形状 + 包裹关系**；位置由 editor 解决。

### 3.5 提供者工作流（纸笔手绘 + 拍照）

Danis 的实际工作方式：**打印底稿 → 手绘 → 拍照数字化**（不用绘画软件）。

```
model_viewer 渲 4 视图底稿 → 打印
   ↓ 手绘衣物（形状 + 包裹关系）
   ↓ 拍照
   ↓ 裁切（按底稿上的对位标记）
4 张方形 PNG
   ↓ 上传 → multiview-to-model
```

**这条链的风险点（必须实测）**：

| 环节 | 问题 | 影响 |
|---|---|---|
| 拍照 | 透视畸变 | Tripo 猜错内参 → 几何歪 |
| 拍照 | 光照不均 / 阴影 / 纸张反光 | 被当成表面起伏 → 几何鼓包 |
| 手绘 | 4 张图之间比例不自洽 | 视图互相矛盾 → 重建扭曲 |
| 去底稿 | 擦不干净（纸纹、铅笔灰） | 边缘残留 → 几何毛刺 |

**可立即改善的措施**：
1. 拍照：**远距离 + 变焦**（减小透视畸变）、正对垂直、均匀散射光（**忌闪光灯**）
2. 打印时在 4 张纸上画**对位标记**（如四角十字），拍照后按标记裁切 → 4 图自动对齐
3. 去底稿：用**「按颜色选择」选中底稿线 → 删除 → 填充白色**，比手擦快且干净

### 3.6 底稿的 alpha 方案（Danis 提出，已讨论）

思路：`model_viewer` 渲染底稿时，**人体像素的 alpha 用特定值**，提供者绘画时
笔画 alpha 恒为 1，再经简单脚本按 alpha 分离 → 得到"只有衣物"的交付图。
**比色键抠图更稳**（颜色会误伤，alpha 是独立通道不重叠）。

⚠️ **但有两个未决问题，必须先实测**：
1. **Tripo 到底吃不吃 alpha？** 官方只说支持 PNG，**未说明 alpha 语义**。
   可能：a) 保留 alpha，透明区域不参与重建 ✅；b) 内部先合成到背景色，
   透明区变黑/白 → 凭空多出几何 ✗。**悲观情况成立则须退化为纯色底**。
2. 若采用照片路线（§3.5），alpha 方案不适用（照片无 alpha 可言），
   只能靠"擦白 + 纯白底"。

**实测顺序（这是整条链路唯一的关键未知数）**：
1. 透明底 PNG → multiview → 看出什么
2. 纯白底 PNG → multiview → 对比
3. 带人的图（对照组）→ 看会不会把人一起重建进去

### 3.7 验收判据（决定方案成立与否）

> 生成衣物后，在 model_editor 里**只做平移 + 缩放（不做形变）**，
> 看能否贴合到 T-pose 人体且不穿模。

- **能** → 说明 multiview 的"形状 + 尺度比例"正确，剩下的确实只是摆位问题 ✅ 方案成立
- **不能**（如缩放后袖子长度比例不对）→ 说明形状本身就不贴合，须回去改参考图规程 ⚠️

**这是一个可测的判据**，应在第二组动工前先跑一次小实验验证（约 40 credits）。

## 4.5 实测记录（2026-09-18）：单图链路通，但复杂植物不可用

### 链路结果：✅ 打通

用一棵橡树的照片（`/james_pm/oak.jpg`，2048²，实际内容是 PNG）跑单图链路：

```
本地审查通过 → 上传 → /generation/image-to-model → 62s success
  → oak.glb (glTF 2.0 合法，PBR 三贴图齐全)
  → jpov_model_viewer --four_views → 4 张预览图
```

**“图 → 3D → 渲染验收”整条链路跑通，工具本身无问题。**

### 但模型质量：❌ 不可用

同一张图分别在 P1 低模 **3,859 面** 与 **19,436 面**（P1 上限 20,000）下出模：

| 面数 | 树干 / 枝 | 树冠 |
|---|---|---|
| 3,859 | 粗糙 | ❌ 碎成飘浮「碎纸片」 |
| 19,436 | ✅ 连续、有粗细变化 | ⚠️ **本质未变**：仍是离散面片堆叠、透空率高 |

**结论：拉满面数只救回枝干，救不了树冠。根因不是面数，是单图重建对
「高自遮挡 + 薄片密集」结构的固有限制**——照片里树叶是互相遮挡的一团，
AI 没有足够信息推断每片叶子的位置与朝向，只能猜。

⇒ **换 H 系列高模（量变）大概率也救不了，不要为此再烧 credit。**

⇒ **植物类资产的正确做法：纸片（billboard / alpha card）+ 透明纹理**
（业界标准；JPOV 已有 `text3d_depth_alpha_*` 验证带 alpha 贴片渲染可用）。

留证资产见 `test/object3d/oak_tripo_negative/`（README 详述，**故意不挂 gold test**）。

### 🔑 方法论结论①：低模必须「先高模再减面」

直接在低面数预算下出模，AI 是在**「压缩」（被迫丢结构）**而不是
**「简化」（保形状减面）**——所以**出来的形状本身就是错的**，再简单也不会对。

```
高模出模（形状正确）→ POST /v3/mesh/decimate 重拓扑（保形状只减面）→ 低模
```

Tripo 有现成的重拓扑端点（Retopology 10~30 credits），**尚未实现**（见 §5）。

### 🔑 方法论结论②：图像端点无 prompt，语言指令在 image-to-image

核官方参数表：`image-to-model` 与 `multiview-to-model` **都没有 `prompt` 字段**，
只有 `text-to-model` 才有。要「既给图又给语言指令」得走 `image-to-image`
（`input` + `prompt` + `inputs[]` 多参考图）。

**但 Danis 决策：不包这一层。** 理由：多一层文本改图 = 多一层不可控，
出问题时说不清是「图没画好」还是「AI 改歪了」。**直接给图，不绕。**

### 🔑 待验证：alpha 通道（官方无说明）

核实结论：**官方文档从未提及 alpha 的处理方式**。`image-to-model` /
`multiview-to-model` 参数表无任何背景/alpha 相关字段；上传端点只说
"Images: JPEG, PNG"。唯一沾边的是 "clean background"（要求干净背景，
**不是**透明背景）。

**推断（非事实，须实测）：alpha 大概率被忽略或先合成到某底色。**
依据：① 参数表零相关字段（对比 OpenAI `gpt-image-2` 有明确的
`background: transparent`）；② ML 管线常见做法是先合成；③ Tripo 的
ComfyUI 生态里有独立的 `Transparent Background` 预处理器——说明**在送进
Tripo 之前**就得把背景处理好，反向支持「Tripo 不吃 alpha」。

**短期决策：用纯白底**（被官方 "clean background" 背书，无未知风险）。
**实测方案（如需要）**：同一张图出白底/透明底两版对照，一次把未知数消掉。

## 4.7 修复：客户端轮询超时导致 credit 白烧（PR #108 内）

**问题**（2026-09-18 wallet 实测暴露）：
1. `poll_deadline_s_` 默认 **180s 太短**——multiview/带贴图任务实测可跑 3min+。
2. 超时/失败的错误信息里**不带 task_id** → 用户/agent 无从续取，只能重跑。

**修复**：
1. `poll_deadline_s_` 180 → **900s**（15min，覆盖绝大多数任务）。
2. 超时与 `failed`/`canceled` 的错误信息**一律带 task_id**，并给续取指引。
3. 新增 **`ResumeByTaskId` / `--resume_task <task_id>`**：拿已知 task_id
   **直接轮询 + 下载，不重新提交**（只发生「查状态 + 下载」两次 HTTP）。
   产图任务额外加 `--to_multiview`。

**验证**：新增 `tripo_client_resume_test`（本地 mock HTTP server 扮 Tripo，
**不烧 credit、不依赖外网**），3 用例 9 断言全绿，并做过 3 项负向验证：
① 去掉超时错误里的 task_id → FAILED；② 去掉 failed 分支的 task_id → FAILED；
③ 让 `ResumeByTaskId` 多发一次请求 → 调用数断言 FAILED。
