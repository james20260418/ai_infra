# JPOV 作为「0 级引擎 / 渲染基础组件」—— 引擎集成定位与架构边界

> 场景：用 JPOV 去搭一个类似 Minecraft 体量的独立游戏。JPOV 定位为「基础组件」「0 级引擎」，
> 在另一个项目里以**静态链接**方式集成，那个项目自己负责游戏引擎。
>
> 本文档记录 2026-09-02 与 Danis 架构讨论的**收敛结论**，供后续 agent 直接采用，
> 避免把已经想透的问题重新想一遍。文档描述以**代码现状**为准（不是 DESIGN.md 里 2026-04 的早期愿景）。

---

## 0. TL;DR（给急读的 agent）

- **JPOV 的 `OneIteration` 不是游戏逻辑主循环。** 它只是一个「受绘制性能影响的低精度输入采样器 + 定频可视化输出点」。逻辑演化必须住在**用户自己的线程**（慢慢演化、不跳帧、不依赖渲染帧率）。JPOV 每帧向用户索取一条「这帧要画什么」，不驱动任何世界状态。
- **世界演化** → 用户自管线程（固定步长逻辑 tick，纯 CPU，可写共享世界快照）。
- **GL 渲染** → 单一生命线（JPOV 的模块线程/主线程）。**永远不要开第二条线程直接操作同一个 GL context**——会打架。
- 多线程模型的铁律：**世界快照数据不碰 GL，GL 上传/绘制统一由持有 GL 的那个线程做**。后台线程只负责算（造 CPU mesh、算物理、跑逻辑），把结果交给「提交队列/共享缓冲区」，由 GL 线程负责提交成纹理/mesh 并绘制。
- **static meshing（后台造 CPU mesh + 主线程一次性上传 + 之后每帧只画静态池）JPOV 现在就支持**，是当前可选且该做的优化。
- **局部更新 / 分层不同频这两件事，JPOV 不改架构去支持**，理由见 §6「明确不改」。不要因此给 RenderCommandList 加「层 / 脏分区 / 差分」概念。

## 1. JPOV 到底是什么 / 不是什么（以代码为准的精确定位）

### JPOV 提供的「包办」其实分三层，只有一层真正「要让渡」：

| 层 | 含义 | JPOV 现在表现 |
|----|------|--------------|
| ① 窗口 + 事件循环宿主 | `Run()` / `RunOnce()`、Xvfb 自启、`Present`/`SwapBuffers`、帧率节流 | JPOV 类持有 |
| ② 输入采集 + 语义折叠 | `CaptureInput` + Click/Drag/Hold 状态机 | JPOV 内部做 |
| ③ 帧内渲染 | `Renderer::Render(cmds, winfo)` 消费 `RenderCommandList`，管 FBO/shadow/HDR/tone map | **已独立于 ①②，是 render-only 入口** |

**关键结论：层 ③（帧内渲染）现在基本已经是「用户给 RenderCommandList，子库把渲染做了」——它就是敞开的核心。**
`Renderer::Render(cmds, winfo)` 不碰窗口、不碰循环、只吃指令。通过 `RunOnce()`（如非窗口截图）等路径已证明 **render-only 路径能独立跑**。

真正需要「让渡 / 明确边界」的是**帧与帧之间的调度主权**（谁决定「逻辑 tick 与渲染帧怎么对齐」），
以及**输入折叠的口味**（JPOV 已替你做了 Click/Drag 语义，游戏输入可能要自己重拼）。

### 一句话定义

> **JPOV 是「每帧全量重建的、纯渲染的基础组件」；它不自带世界、不管理逻辑线程、不拥有逻辑主循环。**

## 2. 线程模型 / GL 单线程铁律

- **GL 只有一条主动渲染生命线。** 在同一 context 上开多线程直接 GL 会有资源竞争 → 禁止。
- **不等于「渲染频率只能 60Hz」**。那条 GL 线程高频率地「醒来看一下要不要全量画」，但大多帧可以做轻活（如只把脏的几张 blit / 只合成几层）。**「高频线程」≠「每帧都重算整张世界图」。**
- 正确分工：
  - **后台线程（用户）**：固定步长逻辑 tick，纯 CPU。可并行造 CPU mesh、算物理、改世界快照。**不碰 GL。**
  - **GL 线程（JPOV）**：负责把后台新提交的东西上传成纹理/mesh，并在渲染帧从最新世界快照取数据画出。
  - **桥**：提交队列 / double buffer / 共享快照。数据（CPU mesh、PNG 字节、世界状态）跨线程传，GL 对象从不跨线程。
- 这是多线程时的**唯一正确姿势**。谁违反「数据不碰 GL、GL 不跨线程」，谁就制造打架 bug。

> 注意：JPOV 代码本身**没有 mutex / single-thread 守卫注释**，它设计上就是「某线程 Init 就在某线程用」。
> 跨线程持有多个 JPOV / Renderer 实例属 GLFW 高阶多窗口玩法，JPOV 未文档化、未验证，**不要指望**。
> 需要多线程时，用上面的「后台 CPU + 主线程 GL + 队列」模式，而不是「开多个 GL 线程」。

## 3. RenderCommandList 每帧全量 vs 分层 / 局部

### 现状（代码为准）

```cpp
// jpov.cc RunOnceInternal()：
RenderCommandList cmds;              // 每帧 new 一个全新的、空的列表
OneIteration(frame, input, winfo, &cmds);   // 用户每帧把整个世界要画的都塞进来
renderer_->Render(cmds, winfo);      // 一次性全量消费执行
```

- `RenderCommandList` 是**每帧从零重建、一次性全量消费**的模型。
- 它没有「跨帧可保留的层」概念，没有「脏分区 / 只重渲变的部分」的表达，没有「静态层可在其上叠高频层」的单位。

### 这对你的几个想要的优化意味着什么

| 优化 | JPOV 现状 | 结论 |
|------|-----------|------|
| **static meshing**（后台造 mesh → 主线程一次性上传 → 之后每帧只**画**静态池，不重造） | 支持：`RegisterMesh`/`RegisterTexture` 上传，mesh 常驻，每帧只填 `Object3DCommand` 引用 | ✅ **现在就能做** |
| **局部更新**（只重渲画面变化的一小块，其余复用上帧） | 不支持：渲染单位是「一整张全量 cmds」，无脏区/复用 | ❌ 不为此改架构（§6） |
| **分层不同频**（2D/秒表高频刷、3D 低频刷、再合成） | 不支持：无「层 + 各层独立脏标 + 合成」表达 | ❌ 不为此改架构（§6） |

> **static meshing 注脚**：`UpdateMesh` 目前实现是 delete + rebuild。对 chunk「脏了就重传」的原型足够；
> 若日后单 mesh 巨大且重传频繁，可优化成流式 buffer 更新——但那属 static meshing 自身的演进，不牵扯 RenderCommandList 模型。

## 4. 何时需要「用户自管调度」（针对游戏引擎）

`OneIteration` 的定位应是 **低精度输入采样器 + 可视化输出点**。若你的游戏只要「逻辑 = 渲染 1:1」的实时逐帧手感，
那**现在就能直接长在 `OneIteration` 里**，JPOV 不绑你。

需要转到「引擎自循环驱动」的明确信号（任一出现即该考虑）：
1. **想要的不是「固定 60fps」，而是「谁掌握『帧时间与逻辑 tick 的关系』这个调度主权」**——例如逻辑固定 50Hz、渲染帧要能从多个逻辑步之间取一个对齐点，而不是被锁成「一帧＝一步」。
2. **想要的逻辑 tick 与渲染帧解耦且可复现**（帧率忽高忽低不抖物理/移动/放置），即「逻辑固定步长 + 渲染插值对齐到逻辑帧之间」。
3. **想要的渲染「这一帧我到底要不要全量画」的决定权在自己**（顶视角/大世界省渲染、后台 tick 不停）。

满足以上时，正确架构是**引擎自己写主循环**，JPOV 只当纯渲染组件，签样式：
```cpp
// 引擎项目里（不依赖 Run() / OneIteration 作宿主）
while (!quit) {
    world.TickFixedStep();            // 引擎自己的固定步长逻辑；慢了就卡，不跳帧
    RenderCommandList cmds;
    world.Populate(&cmds);            // 世界 → 指令（同一张 cmds 缝，原封不动）
    renderer->Render(cmds, winfo);    // 只调渲染，不借宿
}
```
`OneIteration` 里那条 `cmds` 缝一条代码都不用改——它就是两个项目间静态链接时的真实接口。

## 5. 明确「改文档就能解决」 vs 「接口硬天花板」

如果 agent 担心 OneIteration 被误当「逻辑主频」，**光改定性文档 + 用户自跑逻辑线程，就解决 ①②。**
但要注意 **层次 ③（渲染数据模型）是接口硬天花板**——它跟 OneIteration 无关，是「每帧全量 RenderCommandList」本身，
在你要做 static meshing 复用 / 局部更新 / 分层不同频时才会撞上。改定性解不开 ③。

**决策（见下节）：② ③ 里大部分不做，③ 只取 static meshing 这一档（已能做）。**

## 6. 明确不改（重要：防止未来返工）—— 记录 2026-09-02 决策

> 以下结论是**刻意决策**，不是「漏做的功能」。写进文档防止半年后回来重跑这圈讨论。

### 6.1 渲染资源节省：平均功耗 vs 最坏情形

- **局部更新（2）、分层不同频（3）省的是「用户视角不动 / 画面静态」时的平均功耗。**
- **最坏情形（用户持续晃动视角）时，两者对渲染资源几乎没差别**——因为每帧画面都在变，脏区≈全屏，「只重画脏块/复用静态层」无从省起。
- **为避免一个「最坏情形没差别」的收益去动 RenderCommandList 的模型，不值得。**
- **结论：JPOV 不为「视角不动才省」的收益改变「每帧全量绘制」架构。**

### 6.2 那角度中晃动时真正吃香的是什么

- 晃动视角省不了「每次画多少」，只能让「每次绘制本身更便宜」：
  **static meshing + 视锥/背面/遮挡剔除**。
- static meshing 恰恰是「晃动视角下 100% 值得做」的：画的时候不重造 mesh，只看不见的方向不上传绘制。
  它不是「少画几帧」，而是「每帧画得更快」。这条当前架构支持（§3）。

### 6.3 RenderCommandList 不加的概念（本轮拍板）

- ❌ 不加「层」单位、不加「脏分区/局部重渲」、不加「跨帧差分/保留模式」。
- ❌ 不改「每帧全新全量 cmds、一次性消费」模型。
- ✅ 保留 static meshing 所需的资源池化（Register/Update/Release mesh & texture）。

### 6.4 OneIteration 加不加 dt / 可变帧率

- 不为此给 `OneIteration` 加 dt 参数或可变帧率内核。
- 需要的「调度主权」由**用户自管逻辑线程 + 引擎自循环**承担（§4），JPOV 只做那个低精度采样器＋输出点。
- 依赖 wall-clock 的逻辑节拍由用户在引擎线程自己实现，不在 JPOV 回调里硬塞。

## 7. 常见误解纠正（agent 速查）

- ✗「OneIteration 是逻辑主频」→ ✓ 它是低精度输入采样器 + 可视化输出点，不驱动世界。
- ✗「多线程 GL 会打架，所以低刷做不了」→ ✓ 渲染永远单线程；低刷靠「决定低频喂主线程什么 + 慢世界线程写快照」，不开第二条 GL 线程。
- ✗「低刷线程里只能搞 CPU」→ ✓ 对，这是正确且可取的格局（后台纯算 → 主线程提交 GL），不是妥协。
- ✗「分层 = 需要多 GL 线程」→ ✓ 分层是数据/绘制次序维度，一个线程也能分；但 JPOV 现在没有分层单位，且不为它加（§6）。
- ✗「static meshing 需要改架构」→ ✓ 不需要，后台造 CPU mesh + 主线程 upload + 每帧只画，现成支持。

---

## 8. 建议的演进次序（给做 MC-like 的引擎项目）

1. **先用 JPOV（`OneIteration` + 用户自跑逻辑线程）做成「完整、可玩、逻辑对、能漫游能放方块」的第一版世界原型。** 让逻辑剥离 OneIteration、只当采样器这一层用三周内以代码验证。
   此阶段**不需要**为渲染优化重构 JPOV。
2. **做 static meshing**（后台造 chunk CPU mesh → 主线程上传 → 每帧只画静态池，脏 chunk 才重传）——现成支持。
3. **当面（不是现在，是实测撞上）** 真遇到「每帧全量渲染在某规模扛不住」（如顶视角千级区块、大场景懒更新），再带着实测数字决定是否要打开「局部更新 / 分层」那扇门——那是另一轮架构演化，**应由实测触发，不预防性推翻**被多年验证的每帧全量模型。
