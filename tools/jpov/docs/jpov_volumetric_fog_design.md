# JPOV 局部体积雾（Local Volumetric Fog）— 设计文档

> 日期：2026-09-29（v2：加入 tile culling 限流，回应 overdraw 卡顿担忧）
> 状态：设计敲定，待实现（MVP = 球形雾 + 圆柱雾，闭式积分 + tile culling 限流）
> 范围：新增一条**并列于后处理的局部体积雾通道**。MVP 支持球（sphere）与圆柱（cylinder）
> 两种雾体，**一次全屏 pass**（遍历 tile 列表）、**闭式积分**、**tile culling 提供每像素硬上限**。
> 本文档只描述设计，不含实现代码。

---

## 0. TL;DR（给急读的 agent）

- **局部体积雾 = 用户像摆点光源一样在场景里摆「雾体」**（球形 / 圆柱）。
- **渲染 = CPU 建 tile 索引表（仿点光源 tile culling）→ 一次全屏 fog pass**：
  每像素查自己 tile 的雾体列表（**≤ K 个**），逐个闭式积分，就地累加 + 合成
  `L = L_scene · exp(−τ_total) + S_total`（**HDR、tone map 之前**）。
- **闭式积分**：密度剖面限制为「**距离平方的多项式**」，沿视线弦有解析解 ⇒ **零采样、零噪声、确定、可单测**。
- **tile culling 是限流核心**：给每个像素一个 **overdraw 硬上限 K**（否则"1000 团重叠"会炸）。
  - tile 表构建的**加速问题暂未解决** ⇒ **当前的代价旋钮 = 减少 K 或增大 tile 尺寸**（牺牲质量换性能）。
- 用户只能配 **颜色 / 尺寸 / 强度**；衰减剖面是 **JPOV 锁定的菜单**（`kDome` / `kSharp` 等）。
- **MVP 明确不做**：froxel、SDF 沿弦采样、硬边密度、世界 3D 栅格当渲染载体、逐像素 index list、排序。

## 1. 背景与目标

### 1.1 需求（Danis，2026-09-29）

要一个「像点光源一样管理」的**局部体积雾**，用于：

- **工地 / 房间的烟尘弥漫**（若干浓淡不同的雾团）；
- **发光体周围的空气光**（光剑、篝火、灯笼——用发光体颜色驱动雾的内散射）；
- 一般性的局部雾团 / 蒸腾 / 扬尘。

核心诉求：「**给至多 1000 个雾体，像点光源那样摆放，一次画完**」，且**对病态重叠下的 overdraw 卡顿要有保护**（→ §13）。

### 1.2 为什么是「闭式」而不是「射线步进」

| 路线 | 做法 | 代价 |
|---|---|---|
| **射线步进 / SDF 采样** | 沿弦取 N 个样本累加密度 | 采样误差、噪声、**窄特征欠采样→闪烁**、结果依赖采样数 |
| **闭式积分（本文选）** | 密度剖面选「距离平方的多项式」→ 沿弦有解析积分 | 剖面受限于多项式；换来零采样、零噪声、确定、可单测 |

选**闭式**：雾体数量多、要确定、要好测（符合 JPOV「每步可独立自证」的口味），而闭式**没有采样噪声**，gold 图能逐像素锁死。

### 1.3 与「粒子特效 pass」的关系（重要，别混）

本设计与已合入的 **[docs/jpov_effect_pass_design.md](jpov_effect_pass_design.md)**（粒子/火焰 MVP）**不是同一条通道**：

| | 粒子特效 pass | 局部体积雾（本文） |
|---|---|---|
| 载体 | 3D 场景里的**面片 / billboard** | **屏幕空间累加**（一次全屏 pass） |
| 深度 | 测深度、不写 | **不测不写**（穿透几何累加，靠深度裁剪求范围） |
| 混合 | additive / alpha 分批 | **一律加法**（累加 τ / S，末尾合成） |
| 形状 | 逐条命令，每颗粒子一次 draw | **一次全屏 pass**（遍历 tile 列表） |
| 术语 | 效果 = 「数据参数组合」 | 雾体 = 「点光源式的小对象」 |

两者**同属 effect 家族、都自包含子目录**（§10 的组织哲学一致），但**渲染姿态完全不同**，**不共用 shader**。

## 2. 范围与非目标

### 2.1 范围（MVP）

- 形状：**球形雾（sphere fog）**、**圆柱雾（cylinder fog）**。
- 密度剖面：**JPOV 锁定的闭式菜单**（§6）。
- 渲染：**一次全屏 fog pass**；每像素遍历**本 tile 的 ≤K 个雾体**；加法累加 τ / S；就地合成。
- **限流**：**CPU 侧 tile culling**，每 tile ≤ K（§13）。
- 用户可配：**颜色、尺寸、强度**（§4）。
- 平台：OpenGL **3.3 core**（无 compute / 原子 / SSBO，见 §3.6）。

### 2.2 非目标（明确不做，附原因）

| 不做 | 原因 |
|---|---|
| ❌ **froxel 体积雾** | GL 3.3 无 compute；且 froxel 是为「全局大气散射」设计的整屏 3D 网格，局部几团属杀鸡用牛刀 |
| ❌ **SDF 沿弦采样 / 步进** | 引入噪声与「窄特征欠采样→闪烁」；闭式在球/柱上零误差且更省（§6） |
| ❌ **硬边密度（uniform 球）** | 观感穿帮（硬圆盘）+ 无软抗锯齿；菜单只给软剖面。**硬边只在圆柱轴向允许**（端面常被遮/贴结构） |
| ❌ **世界空间 3D 栅格当渲染载体** | 采样分布不对；**密度源**可以世界空间，但**渲染载体**是屏幕空间 |
| ❌ **逐像素 index list / 每像素 8 槽** | 逐像素、GL3.3 无原子难做、且多余。**现在采用「每 tile ≤K 列表」**（Forward+ 式），与前者不同（§3.2） |
| ❌ **排序** | τ 可加、S 一阶可加 ⇒ **顺序无关**（§8.3） |
| ❌ **全局高度雾** | 另一条解析雾（远霾 / 贴地雾），可后续叠加，不在本 MVP |

## 3. 渲染架构

### 3.1 三段式

```
命令层（RenderCommandList）
   │  按点光源的方式携带 std::vector<FogSphere> / std::vector<FogCylinder>
   ▼
CPU tile culling（仿点光源 BuildTileLightIndices，§5）
   │  投影雾体屏幕覆盖 → 填 tile 索引表（每 tile ≤ K，先到先得，重要度预排）
   ▼
GPU 全屏 fog pass（一次全屏三角形）
   │  每像素：查 tile → 遍历 ≤K 个雾体（属性走 buffer texture）→ 闭式 τ
   │  → 局部累加 τ/S → (τ 饱和早退) → L = L_scene·exp(−τ) + S   ← 就地合成
   ▼
（既有）highlight → bloom → tone map → sRGB → 2D UI
```

### 3.2 为什么是「全屏 + tile 列表」，而不是「包围几何 instanced」

早期设想的**架构 A**：把每个雾体画成它的屏幕包围四边形（instanced，加法累加），
GPU 光栅器**免费**替你裁剪到覆盖像素。

它的问题是：**没有每像素上限**。每个片元**不知道自己是第几层**，也**无法在 shader 里自我限层**
（它是 instanced 里的独立实例，fragment 之间无序、互不可见）⇒「1000 团重叠」= 1000 层 ⇒ 爆。

**架构 B（本文选）**：把「每像素该看哪几个雾体」在 **CPU 侧**算成 **tile 索引表**，全屏 pass 只遍历
**本 tile 的 ≤K 个**（Forward+ 式）。这样 **tile culling 同时提供了 culling 与 cap**：

- 概览：**只有"按 tile 截断的列表"能给每像素一个硬上限 K**，这是它相对 A 的唯一但决定性的优势。
- 与灯同构：CPU 侧计算几何、每 tile 上限、调用方预排 —— **与点光源 tile culling 完全一致的套路**（`object3d_renderer.cc` `BuildTileLightIndices`）。

> **与"逐像素 8 槽"的区别**：那版是**逐像素**列表（GL3.3 无原子难做，已否决）；
> 本版是**逐 tile** 列表（CPU 可建、Forward+ 标准做法），**颗粒度粗一档但提供了 cap**。

### 3.3 架构 A 保留为轻量备选

包围几何 instanced（A）仍有价值：**逐像素裁剪精确、无全屏基线成本、无 CPU 建表**。
**信任 CPU 预算（全局 cap + 预合并）**的场景可用它。两版**数学核（§6）完全复用**，只换
「碎片从哪来 + 循环在哪」。**MVP 主路径 = B。**

### 3.4 GPU 一趟干什么（B）

- **一个全屏三角形**（无 per-雾体几何）。
- 片元：由 `gl_FragCoord` + `depth_tex_hdr_` 重建**视线**；查 `gl_FragCoord` 所属 tile 的列表；
  **遍历 ≤K 个雾体**（属性 `texelFetch` 自 buffer texture，§4.3）→ 解弦 → 闭式 τ（§7）。
- **局部累加器**：`τ_total`、`S_total` 直接在当前片元的寄存器里累加，
  **末尾就地合成** `L = L_scene·exp(−τ_total) + S_total` 写出。
- **不需要 MRT、不需要单独合成 pass**（这是 B 相对 A 的简化红利；A 要 MRT 攒 τ/S + 再来一次全屏）。
- **τ 饱和早退**：循环里 `T = exp(−τ)` 已趋 0（雾不透明）就 `break` —— 病态重叠**自己收敛**（A 做不到）。

### 3.5 渲染挂载点

见 §8.2：**在 HDR 之后、tone map 之前**（内散射是光）；与 bloom 的关系：雾在 bloom 前。
全屏 fog pass 读 `depth_tex_hdr_` + HDR 颜色纹理，写回 HDR 颜色纹理（ping-pong，或写入 `out_fbo_`）。

### 3.6 GL 3.3 约束

- **无 compute / 原子 / SSBO** ⇒ **tile 表在 CPU 建**；GPU 侧"scatter 型 append"做不了。
- **无 `glBlendFunci`**（逐附件 blend 是 GL4.0）⇒ 若走 A 的 MRT，两路都加法可用同一 `glBlendFunc(GL_ONE, GL_ONE)`。
- **B 不需要 MRT**，规避此约束。

## 4. 数据模型与公共接口

### 4.1 用户可配（仅三项 + 摆放）

```cpp
// 球形体积雾（点状雾）
struct FogSphere {
    Vec3    center;     // 摆放位置（世界坐标）
    float   radius;     // 尺寸
    Color   color;      // 颜色（介质色 / 内散射色）
    float   intensity;  // 强度（HDR，可 > 1）
};

// 圆柱体积雾
struct FogCylinder {
    Vec3    base;       // 底面圆心（世界坐标）
    Vec3    axis;       // 轴向（单位向量，约定 +Y 为「向上」）
    float   radius;     // 半径
    float   height;     // 高度
    Color   color;      // 颜色
    float   intensity;  // 强度
};
```

### 4.2 JPOV 锁定、用户**不**可配

| 字段 | 说明 |
|---|---|
| `profile` | 衰减剖面，取 §6 锁定菜单（MVP 固定 `kDome`，是否开放选择见 §14） |
| 相位各向异性 `g` | MVP 固定 `0`（各向同性，雾/烟的正确默认） |
| 深度策略 / 混合 / tile 尺寸 / **K** | 全局统一/由 JPOV 调（§13），不给用户 |

> **设计原则**：用户配「颜色 / 尺寸 / 强度」这三项**直观量**；一切**观感/性能风险量**由 JPOV 锁定，
> 避免用户凑出「隐形闪烁」「overdraw 爆炸」这类失败模式（§6.4、§13）。

### 4.3 命令层与属性上传

- 沿用 effect 文档的分层：**命令层无状态快照，不含业务名、不外泄 GL**。
  ```cpp
  std::vector<FogSphere>   fog_spheres;     // 与 point_lights 并列
  std::vector<FogCylinder> fog_cylinders;
  ```
- **雾体的状态**（寿命、飘动、发射器）**不在命令里**，住用户侧。
- **雾体属性走「缓冲纹理（buffer texture / data texture）」，不要 VAO**：
  全屏片元按 tile 列表的 index **随机取第 i 个雾体**，只能 `texelFetch` 纹理；
  VAO 是喂光栅器的**几何/实例属性**，**不能当随机访问的查找表**（那是架构 A 的用法）。
- **每团的 `L_in` 每帧预烘进属性纹理**（§7.2）：雾没有"被照表面"，光照必须在**团**上算一次，而非逐像素。

### 4.4 调用方**必须按重要度预排**（与灯同一约定）

tile 列表"先到先得、满了丢弃"，所以**排序是调用方的责任**（灯的代码注释原话：「用户已按优先级排好序」）。
对雾，重要度建议 `屏幕覆盖 × 强度`（≈ 它对 τ 的贡献）；**近处优先**是个合理近似。

## 5. tile culling（CPU 计算几何，仿点光源）

### 5.1 与现有灯实现同构

参考 `object3d_renderer.cc` `BuildTileLightIndices`（`kTileSize16=16`、`kMaxLightsPerTile=16`）：

1. 遍历雾体（**已按重要度排序**）；
2. 投影到屏幕 → 覆盖矩形 → tile 范围；
3. 向覆盖的每个 tile 写入 index（**先到先得，每 tile ≤ K，满了丢弃**）；
4. 打包进 **tile 索引纹理**，fragment 按 `gl_FragCoord` 查表。

### 5.2 与灯的两处不同（别照抄）

1. **索引位宽**：灯用 uint8（`kMaxTotalLights=255`）。雾要支持 **≥ 1000** ⇒ 索引需 **uint16**
   （`GL_R16UI` / RG 编码），**别用 RGBA8**。
2. **覆盖公式**：灯投"世界 AABB 的 8 角"。雾改用**切线锥解析屏幕半径**（球）：
   `sinθ = r/d`，屏幕半径 `≈ (H/2)·(r/√(d²−r²)) / tan(fovy/2)`。**又快（1 次投影 vs 8 次）又紧**
   （8 角 AABB 比真投影松 → 白写更多 tile）。圆柱用其包围盒 8 角。
   - 跨近平面的退化 → 保守覆盖全屏（宁多勿少）。

### 5.3 覆盖精度

宁可**保守多盖**（否则边缘 tile 漏团 → 漏光/暗带，灯注释里踩过）。多盖的代价只是 GPU 端
几行"进了循环但 ray miss 早退"的空转。

### 5.4 加速：**尚未解决**（现状：降 K / 增大 tile）

tile 建表成本 `≈ Σ_blobs( 覆盖 tile 数 )`，被**大团**支配。加速思路（均未落地）见 §13.5；
**MVP 一律不实现**，**用减少 K 或增大 tile** 作性能旋钮（质量换性能，§13.4）。

## 6. 密度剖面：闭式菜单（JPOV 锁定）

### 6.1 保闭式的唯一窍门：用「距离平方」的多项式

沿视线 `p(t) = o + t·d`，**任何点到中心的距离平方 `|p−c|²` 都是 t 的二次多项式**（无 sqrt）。
所以只要剖面写成 `f(距离²)`、且 `f` 是多项式，被积函数就是 t 的多项式 → **闭式积分**。

> **规则**：剖面用 **`u²`（距离平方归一化）** 写 ⇒ 保闭式；用 **`u` 或 `smoothstep`** 写 ⇒ 丢闭式。
> `smoothstep` 观感最漂亮但**无闭式**，故菜单**不提供**。

### 6.2 球形雾剖面

`u = d/r`（`d` = 到球心距离），弦 `[t0,t1]` 由球求交给出，`L = sqrt(r² − h²)`（半弦长，`h` = 视线到球心的垂距）：

| 剖面 | 形状 | `τ` |
|---|---|---|
| `kDome`：`1 − u²` | 中心最浓、到表面平滑归零的抛物面 | `σ₀ · (4/3) · L³ / r²` |
| `kSharp`：`(1 − u²)²` | 更「芯化」，边缘更快淡出 | `σ₀ · (16/15) · L⁵ / r⁴` |

**深度裁剪仍闭式**（§7.3），用**不定积分**在任意端点求值，不必假设对称弦：

```
kDome  :  F(t) = σ₀ · [ (1 − h²/r²)·t − (t − t_c)³ / (3r²) ]      t_c = 球心在视线上的参数（垂足）
kSharp :  F(t) = σ₀ · [ β²·u − (2/3)βa·u³ + (1/5)a²·u⁵ ]          u = t − t_c, a = 1/r², β = 1 − a·h²
τ([a,b]) = F(b) − F(a)
```

### 6.3 圆柱雾剖面（径向 × 轴向，分离式）

圆柱是**分离式**：`σ = σ₀ · f_r(ρ²/R²) · f_y(y)`（`ρ` = 到轴的横距，`y` = 轴向坐标，局部系）。

**径向 `f_r`**（同球的软边逻辑，`u_r = ρ/R`）：`kDome` = `1 − u_r²`；`kSharp` = `(1 − u_r²)²`。

**轴向 `f_y`**（`u_y = |y|/h`）：

| 剖面 | `f_y` | 次数 / 分段 | 观感 |
|---|---|---|---|
| `kUniform` | `1` | — 最简 | **硬端**（端面可见，仅贴结构 / 被遮时用） |
| `kDome` | `1 − u_y²` | 整段 4 次、**无分段** | 对称软端 → **默认** |
| `kCoreRamp` | `1`（`u_y ≤ c`）+ 平滑降到 0 | **分段**（按 `|y|=c·h` 切 ≤2 刀） | 「柱身均匀 + 两端软」——最像真柱 |

**积分域（三步）**：

1. **径向支撑**：`ρ²(t) ≤ R²` → 一个区间 `[t_a, t_b]`（`ρ²(t)` 开口向上，只有一个谷）。
2. **轴向支撑**：`|y(t)| ≤ h` → 一个区间 `[t_{y0}, t_{y1}]`。
3. **交 + 深度裁剪**：`[T0,T1] = [max(t_a, t_{y0}, 0), min(t_b, t_{y1}, t_depth)]`。
4.（仅 `kCoreRamp`）在 `[T0,T1]` 内再按 `|y| = c·h` 切开。

> **支撑边界正好是剖面归零处** ⇒ 进出边界连续，不跳。

### 6.4 为什么锁定菜单、不给用户自由剖面

- **自由度越高，越容易凑出「高频窄特征」**（如「`r=3` 附近很浓」的环）→ 采样器欠采样→闪烁。
- 菜单**按定义保证**：软、单调/带限、闭式 ⇒ **堵死「隐形闪烁」**。
- minimal-surprise：**界面合法 = 结果可靠**。

### 6.5 角上双零（观感说明）

圆柱用**分离式乘积**，角上（`ρ→R` 且 `|y|→h`）密度**双零** ⇒ 棱角被「削圆」，**通常更好看**。
要**锐角**就得上「到柱面距离场」，含 sqrt ⇒ **非闭式**。**要闭式就必须接受圆润的角**——等价交换，不是 bug。

## 7. 逐像素积分（fragment shader）

### 7.1 视线与求交

- 由片元 + depth 重建世界（或视图）空间视线 `(o, d)`。
- **球**：解 `|o + t·d − c|² = r²` → `disc = b² − cc`（`b = (o−c)·d`，`cc = |o−c|² − r²`）；
  `disc ≤ 0` 早退；否则 `L = sqrt(disc)`，弦 `[−b−L, −b+L]`。**每像素 ~15 flops + 1 sqrt。**
- **圆柱**：局部系下横截面解二次（无限柱）+ 端盖裁 `y` 区间；`dir` 分量接近 0 时走退化分支。

### 7.2 内散射与光照（`L_in` **每团预算一次**，不逐像素）

**关键优化**：`L_in`（雾被照亮的结果）**每帧在团上算一次**（CPU 或一次极小的 pass），存进属性纹理，
fragment 只**读**。因为雾没有"被照表面"，光照不能像灯那样在被照点当场算：

```
L_in = sun_color · shadow(center) · HG(cosθ_sun)
     + ambient_color
     + Σ_point_lights  atten(center) · light_color · HG(cosθ_l)
```

- `shadow(...)`：复用现有 **shadow map**（被山/墙挡住的雾不发亮 → 自然出**光柱**）。
- `HG`：Henyey-Greenstein 相位函数；MVP `g = 0` ⇒ 各向同性（常数）。
- **发光体（光剑/篝火）**：把 `L_in` 换成该发光体自身的颜色（按其亮度衰减）——「用发光体当这团雾的光源」。

→ 每像素只剩「求交 + 一次 exp」，逐像素成本极低（对比：若逐像素采阴影，重叠区会被打爆）。

### 7.3 闭式 τ 与深度裁剪

```
τ_i   = F_i(min(t1, t_depth)) − F_i(t0)      # F 见 §6.2 / §6.3，端点任意 ⇒ 裁剪仍闭式
T_i   = exp(−τ_i)
S_i   = L_in,i · (1 − T_i)
```

- **深度裁剪**：把弦末端 clamp 到场景深度（读现有 `depth_tex_hdr_`）。全在墙后的雾 `τ≈0` 自动消失。
- 读数端：**不测深度、不写深度**（穿透几何累加）。

### 7.4 累加与早退（全屏 pass 内）

- 片元内**局部累加** `τ_total += τ_i`、`S_total += S_i`（无需 MRT）。
- **τ 饱和早退**：`T = exp(−τ_total)` 已 ≈ 0 → `break`（雾已不透明，后面的团看不见）。
- 循环上界 = **本 tile 列表长度（≤ K）**。

## 8. 合成与顺序无关性

### 8.1 合成

在**同一个全屏 pass 内就地完成**：

```
T_total = exp(−τ_total)                   # τ 已累加，只 exp 一次
L       = L_scene · T_total + S_total
```

写回 **HDR 域**（tone map **之前**）——内散射是「光」，必须在线性 HDR 里加，才被 ACES 正确压、
才会被 bloom 吃掉光晕。亮度对齐现有 `LIGHT_INTENSITY.md` 锚点。

### 8.2 与现有链路的位置

| 顺序 | pass | 说明 |
|---|---|---|
| ① | 3D 不透明（sky → Object3D → SkinnedMesh → 图元 → 文字 3D） | 测+写深度 |
| ② | **体积雾（本 pass）** | 不测不写；读 `depth_tex_hdr_` + HDR 颜色 |
| ③ | highlight pass（现有） | |
| ④ | bloom（现有） | 光柱 / 烟晕被 bloom 打光 |
| ⑤ | tone map + sRGB（现有） | |
| ⑥ | 2D UI（现有，永远最上层） | |

### 8.3 顺序无关性（为什么不用排序）

- **总消光可加、顺序无关**：`∏exp(−τ_i) = exp(−Στ_i)`。累加 τ 后**只 exp 一次**。
- **内散射一阶可加**：`S_i = L_in,i·(1−T_i)`，稀薄时 `Σ S_i` 即正确；浓雾重叠略偏亮（一阶近似），可接受。
- ⇒ **所有雾体无需排序**（对比 alpha 粒子必须从远到近排）。注意：**tile 列表里的"顺序"只决定
  cap 时保留谁（重要度），不参与合成顺序**。

## 9. 确定性与可测性（JPOV 的命门）

### 9.1 顺序与浮点

- 全屏 pass 内**逐像素固定顺序**遍历 tile 列表（列表顺序 = 重要度序，确定）。
- 浮点加法非结合 → 依赖固定遍历顺序；**llvmpipe 确定** ⇒ **gold 图可复现**。
- 上真 GPU / 换后端要留意（与 A 的 instanced 加法同理）。

### 9.2 对比：闭式 vs 采样

闭式**无随机、无采样** ⇒ 天然确定；这正是选它而非 SDF 采样的重要原因之一。

### 9.3 可单测

- **闭式积分核**（§6 的 `F`、`τ`）是**纯 CPU、GL-free** 的数学，可独立单测（含向量 fuzz）。
- **tile culling**（§5）是纯 CPU，可单测（重叠、cap 截断、覆盖不漏）。

## 13. 性能与限流（overdraw 专题）

### 13.1 为什么要怕 overdraw：透明/雾**吃不到 early-Z**

- **不透明**：层间**写深度** → early-Z 逐片元剔除；前到后排序时**每像素只着色 1 次**
  （随机顺序期望 `H_N ≈ ln N`）。所以大不透明物体不卡。
- **透明 / 雾**：层间**不写深度**、**每层都要参与混合** → **无论什么顺序都 `E[着色层数] = N`**。
  **early-Z 完全失效**。
- 结论：**"覆盖全屏"不是元凶，"顺序 + 透不透"才是**。雾是**固有 overdraw**，只能靠 **cap / 限提交**。

（`H_N`：N 个随机深度层里"新最小值"的期望个数 = 第 N 调和数。前到后 = 1，后到前 = N。）

### 13.2 tile culling = **局部 cap**，这是它的核心价值

- **全局 cap**（只提交前 K 个团）能兜底 worst-case（≤K），但**太粗**：稀疏场景里会**丢掉"局部重要"的团**。
- **tile cap**（每 tile ≤ K）既**局部精确**又**给硬上限**：稀疏处照常显示全部团，密集处每像素≤K。
- 所以 **tile culling 必须带上**（本 v2 的核心变更）。

### 13.3 tile 表构建的成本与"加速未解"

- 成本 `≈ N · Ā / s²`（`Ā`=平均团屏幕面积，`s`=tile 边长）+ O(N) 投影 + O(N logN) 排序。
- **被"大团"支配**（大团覆盖 tile 多）。
- **加速方案（§13.5）暂不落地** ⇒ **当前代价旋钮 = 减少 K 或增大 tile**（§13.4）。

### 13.4 性能旋钮：**减少 K / 增大 tile**（质量换性能）

- **K（top 几）**：直接把 GPU 上界钉成 `屏幕像素 × K`。
  - **雾会饱和**（叠几层后 `T→0` 已不透明）⇒ **K = 8~16 通常就够**，再加白烧。
  - 压 K → 更省 GPU（也更省，因 cap 后 CPU 写入也变少）。
- **tile 尺寸 `s`**：**CPU↓ / GPU↑ 的旋钮**。
  - CPU 建表 `∝ 1/s²`（越大越省）；GPU 端每像素要遍历"盖到本 tile 但 miss 本像素"的多余团 `∝ (2r+s)²`（越大越费）。
  - **最优点 ≈ 平均团的屏幕半径**；实践取 **`16×16` 或 `32×32`**。`s` 明显大于团半径 → 纯浪费 GPU。
- **数量级参考**（1920×1080，1000 团、平均屏幕半径 ~50px）：

  | tile s | 格数 | CPU 列表条目 | 总 GPU 评估 |
  |---|---|---|---|
  | 8 | 32400 | ~196K | 12.5M（≈6× 屏幕） |
  | **16** | 8160 | ~49K | 12.5M（≈6×） |
  | **32** | 2040 | ~25K | 25.6M（≈12×） |
  | 64 | 510 | ~9K | 36.9M（≈18×） |

  → `s=8` 白费 CPU（GPU 与 16 相同），**别选**；`s=16` 或 `32` 是甜区。
- **对比其它渲染过程（数量级）**：雾 GPU ≈ **1–3 个全屏 pass**；雾 CPU culling ≈ **0.1–1ms**；
  即 **≈「多一个全屏 pass + 亚毫秒级 CPU」**，**可接受、非免费**。
  ⚠️ **llvmpipe（软件）下乘 ~50–100×** → CI/软件渲染时只能靠**小 N + 小 Ā**。

### 13.5 限流手段对照表（含**未落地**的加速思路）

| 手段 | 省 shader | 省覆盖/光栅 | 成本 | 状态 |
|---|---|---|---|---|
| **tile cap（本文选）** | ✓(≤K) | ✓(只提交 ≤K/像素) | CPU 建表（未优化） | ✅ MVP |
| 全局 cap（只提交 top-K） | ✓ | ✓ | 低排序 | ✅ 兜底 |
| CPU 预合并重合团 | ✓ | ✓ | 低 | ✅ 建议（加法⇒合并精确） |
| stencil 逐像素 cap | ✓ | ✗（仍光栅全 N） | 低 | ⚪ 备选（配架构 A） |
| 大团走全局列表 | ✓ | ✓ | 中 | ⚪ 后路（大团是成本元凶） |
| tile 表构建 GPU 化（小 FBO + `GL_MIN` / depth K 趟） | — | — | 已探、收益不确定 | ⚪ 后路 |

**未落地的加速思路（仅记档）**：
1. **切线锥解析覆盖**（§5.2）—— 快且紧，**建议直接做**（不算"加速难题"）。
2. **放大 tile**（§13.4）—— 即本轮的"降质量"旋钮。
3. **大团单独走全局列表**：把覆盖 tile 数超阈值的"大团"写进**一张全局列表**（1 条），fragment 遍历
   「全局列表 + 本地列表」→ 把建表的 `Σ(团×格)` 降到 `O(团数)` 级。
4. **CPU 并行**：tile culling 是纯 CPU、不碰 GL，可按团分片多线程。
5. **GPU 侧建表**：缩小 FBO（1/16 → 1/256 像素）+ instanced 画团 quad + `GL_MIN` 取最小 index；
   K 槽需 **K 趟**（每趟"只保留比上一趟阈值大的最小 index"）；depth 版用 `gl_FragDepth=index` + discard
   阈值 + `GL_LESS`（**不依赖浮点 min-blend**，更稳）。**注意**：这正是"透明/覆盖"问题，**吃不到 early-Z**
   （要早测就得有 index 当 z，写 FragDepth 又把早测关了——死循环）；且 **llvmpipe 下未必更快**。

### 13.6 调用方**必须按重要度预排**（同 §4.4）

cap 的取舍顺序 = 数组顺序（先到先得）。**调用方预排**（近处/高贡献优先），否则被丢的可能是最重要的团。

### 13.7 早期讨论结论（防重复推演）

- **instancing 只是"同质 + 顺序无关"的特权**：状态（blend/shader/纹理/深度）或几何一变就得拆 draw。
- **A 的 in-shader 自我限层做不到**（fragment 不知自己是第几层）；要用 stencil 数层或改 tile。
- **early-Z** 对 tile 建表 pass **无关**；`discard` / `gl_FragDepth` 只关**含它的那条 shader**的 early-Z，
  **不影响主渲染的干净 opaque shader**。
- **Vulkan"默认 late-Z"是语义，不是硬件不早测**：干净 shader 仍享 early-Z。

## 附：本设计讨论结论来源

本设计由 2026-09-29 与 Danis 的多轮讨论收敛而成。

**v1（形状 + 闭式 + instanced 累加）关键决策：**

1. 从「屏幕空间解析雾」起步，扩展到「局部体积雾」。
2. 选 **闭式** 而非 SDF 采样：保确定、可测、零噪声。
3. 只做 **球 + 圆柱**（放弃 box 的自由度，换闭式与清晰）。
4. **否决**「逐像素 index list / 8 槽」（多余且 GL3.3 难做）。
5. 「发光 = 光晕（bloom）+ 空气光（体积雾）+ 照明（发光体当光源）」三个职责分开。
6. 密度剖面是 **JPOV 锁定菜单**，用户只配 color/size/intensity。
7. 圆柱 = 径向 × 轴向**分离式乘积**；角上双零（削圆）是闭式的等价交换。
8. 顺序无关（τ 可加、S 一阶可加）⇒ 不排序。
9. GPU 端无随机、无采样 ⇒ llvmpipe gold 图可逐字节复现。

**v2（加 tile culling 限流）关键决策：**

10. **overdraw 担忧**：透明/雾吃不到 early-Z（`E[着色层数]=N`）⇒ 必须 cap。
11. 架构从「纯包围几何 instanced（A）」改为「**全屏 + tile 列表（B，Forward+ 式）**」——
    只有 tile 列表能提供**每像素硬上限 K**；A 保留为轻量备选。
12. tile culling 与点光源同构（CPU 建表、每 tile ≤K、调用方预排）；两处不同：**uint16 索引** + **切线锥覆盖**。
13. 雾体属性走**缓冲纹理**（随机访问），**不是 VAO**；每团 `L_in` 每帧预烘。
14. B 顺带简化：**不需 MRT、不需单独合成 pass**，且能 **τ 饱和早退**。
15. **tile 表加速未解** ⇒ 当前旋钮 = **减少 K / 增大 tile**（雾会饱和 ⇒ K=8~16；s=16/32）。
16. 其它限流/加速（全局 cap、预合并、stencil cap、大团全局列表、GPU 小 FBO 建表）记档未落地。
