> 结论先行：**「纯天球解析云」这条路走得通**（只改 sky shader + 一个可选的光照耦合），
> 但**五种方案里没有一种能同时做到"便宜、像、无伪影"**。我的排序与具体教训见文末。

## 1. 五个方案

| # | 名字 | 做法 | 成本（相对） | 观感 |
|---|---|---|---|---|
| 1 | `kPlaneFbm` | 球极投影 + 4 octave fbm + 大尺度云量起伏 | 1× | 碎积云/层积云，分布自然但偏糊 |
| 2 | `kWorley` | Worley F1（域扭曲）+ fbm 细节 + patch | 1.5× | 团块最清楚、最有"积云"味；边缘易"剪纸" |
| 3 | `kCirrus` | 各向异性拉伸 fbm（6:1）+ 域扭曲 | 1× | 卷云/丝状，留白通透、**几乎没有伪影** |
| 4 | `kPlanes` | 3 层不同尺度/偏移的平面云合成（over） | 3× | 有层间遮挡与视差，当前最"干净"的一档 |

相机 φ = −0.2（仰视 12°），只拍天空（`SetShowScene(false)`）。

## 2. 踩过的坑（都是"看起来对、实测错"的那种）

1. **平面投影 `dir.xz/dir.y` 不能用**：`dir.y→0` 时噪声频率发散 ⇒ 地平线一圈**径向拉丝**；
   天顶收缩成一点 ⇒ 放射状串珠。换成**球极投影** `dir.xz/(1+dir.y)`（共形）后消失。
2. **scale 的单位是"1/立体角"不是"米"**：初版 `scale=1` 整片天空只有 2~3 个噪声胞元 ⇒ 一团模糊。
   实际需要 4~9。
3. **「朝光源偏移一次采样」不能当自阴影**：这个量近似等于"我是不是在云的边缘"
  （边缘朝哪都低）⇒ 每朵云都是**黑心 + 亮边**，正午看起来正是"上暗下亮"的倒错。
   改成**密度梯度造 2.5D 法线 + N·L** 才对（代价 4 次额外密度采样）。
4. **法线符号**：从下往上看云时，屏幕上方 = 更靠太阳那侧，应该更亮 ⇒ 用 `+grad` 而不是 `-grad`。
5. **云板光线步进（12~20 步）在 2D 噪声上必然出条纹**：沿视线方向噪声根本不变化 ⇒
   同一片云被拉成竖直长条；逐像素抖动会把条纹换成颗粒（IGN 还会留 54° 菱形网点），
   斜切只是把条纹转 45°。**真解是 3D 噪声**（llvmpipe 上 20 步 × 3 octave × 8 hash 太贵），
   本轮退化成「3 层视差平面」。
6. **消光取太大会变成"一张灰幔"**：整层光学厚度 3× 时 alpha 处处→1，云失去形状。
   1.2× 才能看到边缘半透、只有云心饱和。
7. **云的亮度必须从天光推导**（`cloud_bg = Preetham 散射 × season × intensity`），
   否则改 intensity / 浊度 / 季节时云不跟着走，一眼穿帮。
8. **GLSL `const int x = <uniform 表达式>` 不是常量表达式**（这个工程里第二次踩）。
9. **加字段到 `SkyCommand` 必须放最后**：它是聚合初始化的（`SkyCommand{太阳方向, 浊度, …}`），
   插在中间会静默改掉所有调用点的语义。

## 3. 太阳遮挡（不需要 CSM）

两层机制：

1. **alpha over** 天然遮住背景（含日盘）；
2. 日盘亮度 ~2e5 × 天空，和云的 radiance 差 5 个数量级 ⇒ α=0.9 时仍会透出 2e4 的亮斑。
   故对**发光天体**另加一个强指数：`cloudLightBlock(sun_dir) = mix(1, exp(-14·d·opacity), sun_occlusion)`。
   月盘同理（夜里它才是主天体）。

实测（`cloud_light_off.png` / `cloud_light_on.png`）：只做①时"天上挂着云、地面却是硬阴影高对比晴天"；
把**云量接到光照**上（直射 ×(1−0.85c)、ambient ×(1+0.35c)）后阴影被填充、整体变暗、口径统一。

⚠️ 这条耦合现在放在 `demo/skylight_scene.h`（云量由 CPU 同源噪声给出）。
真工程化应下沉到 `SkyCommand::SunDirectionalIntensity()` 之类的地方，
但那样 `render_command.h` 就要依赖噪声实现 —— **这是本次最值得讨论的架构问题**。

## 4. 仍未做 / 已知局限

- 云不投影到地面（无 CSM）、云不改 ambient 的**颜色**、云不调制 Preetham 的太阳散射项
  （被遮住时天空散射不会变暗，等价"日食不全黑"）。
- 3D 噪声 / 体积云没有做（llvmpipe 成本 + 无纹理约束）。
- 云的时间演化用 CPU 累积的 `wind_offset`（确定性、帧率无关），没有做形态演化（云不会长/散）。
- 夜景的云整体偏平（缺月光边缘光 + 星光）。
- 正午地平线那条"粉带"是 Preetham 既有行为（无云时也在），不是云引入的。

# 第二轮（18:50 之后）：为什么前 5 个方案都像"贴纸"，以及真解

Danis 的判断是对的：**前 5 个方案漏了整个体积管线**。它们把云写成**方向函数** `d(dir)`，
等价于在球面上贴一张 2D 图 —— 上半球每个方向只有一个采样值，**没有任何垂直结构**：

- 没有"云底平面"（真实积云的凝结底在同一高度，是"层"的最强视觉线索）；
- 没有厚度与视差（相机俯仰时云完全不动）；
- 没有云内的自阴影（只有一张表面法线，永远只能做出"浮雕"）。

## 业界配方（查证）

Nubis / Horizon Zero Dawn（Schneider 2015）、Hillaire 2020、以及各家引擎实现都是同一套：

1. **密度场是 3D 的**：`d(x,y,z)`。Perlin-Worley base + Worley detail（无纹理时用解析 3D fbm/值噪声）。
2. **云层是固定的世界高度区间** `[BaseAltitude, BaseAltitude + Thickness]`，不是"相机上方的偏移层"
   —— 这样飞机/相机上下移动时层不动，视线俯仰只改射线。两条世界高度平面求交，analytic。
3. **垂直剖面 analytic**：积云 = 平底 + 圆顶（stratus 薄而均匀、cumulonimbus 上翻）。**底平是关键线索。**
4. **天气图**（大尺度 2D 噪声）控制"哪里有云"，决定 coverage 的空间分布 —— 真实天空是成片的。
5. **沿视线 front-to-back 步进积分**；沿光方向再步进 2–4 次求自阴影；HG 双瓣相函数 + 多次散射近似。
6. **高度切变**（wind shear）：云的上、下截面错开 ⇒ 立刻"立体"。
7. 地平线附近积分上限远超几十公里 ⇒ 用 distance fade 把截断藏进霾里；不要用"pitch 衰减"代替它。

两个容易踩的参数：
- **长宽比**（friends-graphics 的 `ShapeAspectPercent`）：某版本把垂直重复设成水平的 3 倍，云全部被压成扁饼。
  用**世界空间各向同性**的 3D 噪声即可（本实现就是这么做的）。
- **步进抖动**：周期型抖动（IGN 是 54° 斜纹）会在云上留下菱形网点；用整数白噪声。

## 本仓库的实现（scheme 6 = `kVolume`）

`cloud_shader.h` 新增：`cloudHash3 / cloudNoise3 / cloudFbm3 / cloudDensity3 / cloudPhase / cloudSampleVolume`。

- 层：`layer_height_m = 1200`，`layer_thickness_m = 1400`（积云尺度），两条世界高度平面求交；
- 密度：天气图（2D `cloudFbm`）× 3D `cloudFbm3`（特征 850 m，3 octave）→ 阈值 → 垂直剖面 → 细节侵蚀；
- 步进：20 步 + 逐像素整数白噪声抖动；`kFarLimit = 30 km` + far fade；
- 光照：每步 2 次光程采样（180 m / 520 m）→ `exp(-od)`，HG 双瓣（g=0.65 / −0.18）归一化，
  多次散射近似 `0.65·exp(−0.3·od)`；
- 成本：每像素 ~20×(3 层 3D fbm + 2 次光程) ≈ 0.6–1 s/帧（llvmpipe，1280×720）。
  实时交互需要半分辨率 + 时域重投影（这一步没做）。

**效果**：抬头 30° 那张能直接看到"云层底面 + 厚度 + 视差"，这是任何 2D 方案都做不到的。
剩缺点：云缘颗粒（抖动）、云内细节偏少（3 octave 上限）、夜景缺月光方向性、
地平线以下仍是占位纯色（这是场景/地色的事，不是云的）。

## Blender 侧（Danis 问的）

Blender 没有"解析天空球云"的官方能力（内置 Sky Texture 是 Nishita，只算大气，不含云）。可参考的插件：

| 插件 | 做法 | 对我们的价值 |
|---|---|---|
| Physical Atmosphere² / Physical Starlight and Atmosphere | 程序化大气 + **体积云**（noise 驱动），物理光照 | 观感/曝光参考；算法同 Nubis 路线 |
| Real Sky (Marco Pavanello) | 物理天空 + 四类程序化云（Cirrus/Cirrocumulus/Altostratus/Cumulus） | **云分类**与参数命名的好参考 |
| Easy Clouds / Clouds Pro / Volumetric Clouds Generator | 节点/几何体做云 | 美术向，不涉及实时解析式 |

结论：**Blender 侧没有可以直接抄的"解析云"实现**——它们都是体积着色（体积材质 + 噪声纹理），
和我们 scheme 6 走的是同一条物理路线，只是它们有 3D 纹理和蒙特卡洛积分。
真正可抄的是第 1 节那套**结构**（固定高度层 + 3D 密度 + 垂直剖面 + 光程），而不是某个插件。

## 离线纹理素材？（Danis 提的可选项）

真要再往上走一档，最划算的是**离线烘焙可平铺 3D 噪声**（Perlin-Worley 128³ + Worley 32³），
运行时 `texture3D` 采样替代解析 3D fbm：

- 好处：同样的观感，成本降到 1/2~1/4（3D 纹理采样 vs 8 角点 hash × 3 octave），能上交互帧率；
- 代价：引入一个"素材"，不再是纯解析 —— 但**生成过程仍是解析的**（compute/CPU 生成，无人工绘制）；
- 与"不留纹理"的原则冲突，需要 Danis 拍板。

# 第三轮（19:07 之后）：s6 的观感修正 + **无缝循环飘动**

Danis 反馈：s6 路子对，但 ① 云阴影细节不足、大片发白；② 云层"偏低"；③ 要求**随风一直飘、能循环播放**。

## 1. 观感修正（都在 scheme 6 里）

| 症状 | 原因 | 改法 |
|---|---|---|
| 大片发白 | 阈值 softness 0.26 太软 ⇒ 到处都是"薄云"；环境项 0.24×bg 让云和天空一样亮 | softness→0.12；ambient→0.045–0.10×bg；加密度 AO `sun *= mix(0.55,1.12,1−d)` |
| 阴影细节少 | 只有 2 个光程样本 + 单次散射 | 3 个光程样本（140/420/1100 m）；多次散射三项 `0.55e^{-0.35τ} + 0.25e^{-0.10τ}` |
| 层次平 | 3 octave | 形状 4 octave + 细节侵蚀 2 octave（4× 频率）|
| 云层偏低 | 层底 1200 m、特征 850 m | 层底 **2400 m**、厚 1800 m、特征 **1200 m** |

## 2. 无缝循环飘动（本轮的硬需求）

**做法**：把 3D 噪声场做成**周期化**的（格点按 `period` 环绕），于是世界里平移 `period` 个胞元后
整个场逐像素回到原状。风偏移由 CPU 按时间算成 `0..period` 的确定性偏移，一个周期正好走完。

- shader：`cloudHash3p(ivec3 p, int period)` + `cloudNoise3p` + `cloudFbm3p`；
  每层用**轴置换**（`p.zxy*2`）而不是旋转 —— 旋转会破坏格点对齐、周期性失效；
  `period` 随层翻倍，与 lacunarity=2 配套。
- 常数：特征 1200 m × 周期 16 胞元 = **19.2 km/圈**；`kCloudLoopSeconds = 600 s` ⇒ 32 m/s（延时感）。
- 细节侵蚀层用 **2× 风速**（且 2 是关键整数倍，周期性仍成立）⇒ 云一边整体平移、一边"翻滚"，
  不是一块板子在平移（"风起云涌"）。
- **验收（硬指标）**：`loop_0.png` 与 `loop_6.png`（t = 0 与 t = 600 s）**md5 完全相同**
  （`b53038f8c47c9424baa92694afbf77fd`）⇒ 循环点零跳变。

## 3. scheme 7 = 积云 + 高空卷云

在 s6 之上叠一层 8200 m、700 m 厚、特征 2.2× 的薄卷云：给天空"加高度"，且高层会压在下层云上
产生纵深。成本 +8 步（约 +35%）。

## 4. 现在还剩什么

- 正午亮部对比偏柔（ACES 把高光压平），要更"透亮"得动 tone map 或提高云的 HDR 峰值；
- 卷云形态偏"高积云膜"，不是纤维状（缺少各向异性拉伸 + 更细的侵蚀）；
- 地平线以下仍是场景的占位纯色（不是云的问题）；
- 实时帧率：每帧 ~0.6–1 s（llvmpipe 1280×720），交互需半分辨率 + 时域重投影，
  或离线烘焙可平铺 3D 噪声纹理（仍是程序生成）。

# 第四轮（19:18 之后）：s1–s4 升级成体积链路 + 云高标尺场景

Danis 的判词：s5 光照比 s7 好；s7 云底像"平面塑料板"；s5 云偏矮；s1–s4 还是"少了体积链路"的低幼感，能救就都升级成完全体再比。

## 1. s7 云底发平的原因与修法

云底是**层底平面**，看过去所有点的光程（到太阳）几乎一样 ⇒ `od` 饱和、亮度拉平。
三条改法（都落在 `cloudDensity3` / `marchCloudLayer`）：

- **底部侵蚀加强**：`erode = mix(0.55, 0.22, smoothstep(0, 0.35, h))`（真实积云底面是被上升气流撕碎的）；
- **光程样本 2 → 3**（140 / 420 / 700 m），近程项负责"薄处透光"；
- **密度 AO** `sun *= mix(0.55, 1.12, 1-d)`，厚处压暗。

效果：塑料感大减，但主层云底仍偏"片状"——这是 3 octave 上限 + 粗步进的锅，要再进一步得加细节层或降分辨率+时域。

## 2. s1–s4：同一体积链路，只换密度场（"完全体"）

| # | 密度场 | 观感 |
|---|---|---|
| s1 | 3D fbm（4 octave） | 基准积云 |
| s2 | 3D **Worley F1**（域扭曲 + fbm 混合） | 花椰菜团块；仍偏"乒乓球"，单元尺寸太均匀 |
| s3 | **各向异性**（x0.45 / y1.9 / z1.6） | 层云/高积的丝缕感，方向性明确 |
| s4 | **域扭曲**（低频 fbm 掰弯域） | 轮廓最不规则、最像真云（本轮最佳形状） |
| s5 | **保留老的 2D 多层** | 光照最"讨喜"（达西喜欢），但**没有高度/视差** |

s1 与 s6 现在等价（同 kind、同层参数）⇒ capture 只拍 s1（s6 保留为代码路径）。

## 3. 云高标尺场景（`SetCloudScaleScene`）

12 km 大地（40×40 quad × 300）+ 4 座 460–900 m 的"台地"（放大方块，3.8–7.6 km 远）+ 近景 1 m 方块。
**两个必须踩过的坑**：

1. `camera.far` 默认 **1000 m** —— 12 km 大地与 5 km 外的台地被整段裁掉，看起来像"无限延伸的死灰板"。
   标尺场景要放到 40 km（`scene_far_m_`）。
2. 太阳方位不能放在相机前方：台地全成背光剪影，读起来像地平线上的黑洞。放到相机背后（方位 30°）。

对照结论（`scale_strip.png`）：s5（2D）的云到地平线**不压缩、不收敛**，像贴墙；s2/s7（体积）能看到
云底向地平线收敛 + 分层 —— 这就是"体积 vs 贴纸"最直观的证据。

## 4. 循环仍然是硬验收

# 第五轮：云配置进天光 viewer 面板

保留 **s1 / s2 / s3 / s4 / s7** 五个体积方案（s5 的 2D 版退役，只留在 capture 里做对照）。

## 面板（左上角独立一块）

| 控件 | 语义 |
|---|---|
| 云方案（下拉） | 关 / s1 fbm / s2 Worley / s3 各向异性 / s4 域扭曲 / s7 +高空卷云 |
| 云量·密度 | `CloudCommand::coverage`（阈值偏置，0 = 晴） |
| 云层底高 m | `layer_height_m`（600–6000；s7 的高层跟着它 ×3.4） |
| 风向 ° | 漂移方向（水平方位角） |
| 风速 m/s | 决定循环周期 `T = 19.2 km / speed` |

**为什么云面板不塞进主面板**：主面板已经 17 行（≈488 px），再加 5 行会盖住屏高 80%，
正好压掉地平线——而地平线是判断云高最关键的地方。

## 两个实现细节

1. **时间驱动要能关**：交互模式 `cloud_time_s = frame_count/60`；capture 用
   `SetCloudTimeFromFrames(false)`，否则逐张指定的 t 会被覆盖，循环验收直接失效。
2. **任何风速都无缝**：偏移量按 `mod period` 给，`T = kCloudDriftM / speed` 自动成立。
   改**风向**时云会"跳"一下（偏移向量被旋转）——预实验阶段接受；要平滑得把方向也做成
   时间插值。

`--capture-cloud-ui <dir>` 出一张带面板的图用于核对排版（`clouds_exp/cloud_ui.png`）。

# 第六轮：噪点与「分辨率突然不行」的根因 + 带限 / 像素锁定细节

Danis 的判词：「5 个云都有噪点，这个分辨率问题堪忧，这是纹理就这样的、没法继续解析了吗？
我需要它解析的一个大目标就是让它**足够细腻**，没有那种分辨率突然不行的情况。」

## 1. 结论先行：这不是「纹理分辨率」问题，而是**采样**问题

解析云没有纹理，所以「贴图分辨率到顶了」不成立。噪点来自三个我们自己选出来的采样行为：

| # | 机制 | 量级（本实现） |
|---|------|----------------|
| ① | **octave 数写死**，不管一个像素跨多远 | 第 4 octave = 150 m 胞元 |
| ② | **体积积分步长太粗** | 20 步 ⇒ dt 150–1500 m（近地平线） |
| ③ | **逐像素白噪声抖动**（1 spp） | 每像素独立 ⇒ 就是"椒盐" |

①+②合起来的判据：噪声胞元 150 m，步长 180 m ⇒ 每步跨过 1.2 个胞元，**已过 Nyquist**
⇒ 该 octave 采出来就是白噪声；再叠加③的抖动，就成了肉眼看到的「噪点」。
近地平线时像素足迹按 `t/dir.y` 放大到 ~1 km，噪点成片 ⇒ 就是「分辨率突然不行」。

**实测基线**（`--capture-clouds`，1280×720，天空区 |3×3 高通| > 3 LSB 记为噪点像素）：

| 图 | 噪点像素占比 |
|---|---|
| s1/s2/s3/s4 noon | 6.6–7.3 % |
| s7 noon（+高空卷云） | 11.5 % |
| s7 sunset | 23.1 % |
| s1 sunset / night | 12.8 % / 18.1 % |

## 2. 改法（三件，都落在 `cloud_shader.h`）

### 2.1 带限 fbm（均值保持）

`cloudFbm3pLod / cloudFbmLod`：按 `fp`（每像素跨过多少个基频胞元）逐层求权重
`w = clamp((0.5 − fp·freq) / 0.25, 0, 1)`，`w=0` 时**不采样、直接吃该层均值 0.5**。
归一化 fbm 均值恒 0.5 ⇒ 丢细节既不变暗也不变薄，退化连续（不会突然糊/突然暗）。

### 2.2 两个足迹必须分开：**像素足迹**管抗锯齿，**步长**管积分精度

第一版把 `fp = max(dt, t·dθ/dir.y)` 混在一起 ⇒ 细节连同走样一起被抹掉（视觉判词：发糊）。
正确做法：

- `fp` 只用**像素足迹** `t·dθ/dir.y`（dθ 由 `length(dFdx(dir))` 取，统一控制流里算）；
- 步长只影响积分精度：20 → 32 步（实测 32 与 64 步差异 <1%，说明瓶颈不在这里）。

### 2.3 像素锁定的细节层（「细腻」的真正来源）

普通 fbm 的高频层振幅 ×0.5 衰减：第 7 层只剩 1/128 ⇒ **加 octave 不会变细腻**
（实测 5 层 vs 7 层逐像素几乎一致，1–2px 能量 0.48 vs 0.47）。

改法：`cloudDetailSelfSimilar()` —— 噪声**胞元尺寸锁定在屏幕上约 7 px**（±15% 交叉淡化），
**振幅不衰减**，两层（7 px + 14 px，权重 0.65/0.35）叠加读成"绒毛/纹理"而不是"磨砂膜"。
频率取 2 的整数次幂 ⇒ 云场仍严格可平铺，**`loop_0.png` 与 `loop_6.png` 的 md5 依旧相同**。

关键：细节必须加在**阈值之前**（扰动形状标量，云边才会被纤毛化）；加在阈值之后只会被
沿视线的积分平均掉（实测 1–2px 能量只涨 10%）。

附带：`soft`（覆盖率过渡宽度）随「细节被丢掉的比例」自动放宽（`cloudLodKeep`），
否则"近处锐利 / 远处糊成一片"的交界会露出一条硬边 —— 那也是「分辨率突然不行」的形态。

## 3. 实测（同一机位、同一时间）

| 图 | 噪点像素%（前 → 后） | 1–2 px 能量 | 4–10 px 能量 | 平均亮度 |
|---|---|---|---|---|
| s1 noon | 6.62 → **0.33** | 1.60 → 0.56 | 1.00 → 0.75 | 221.5 → 223.6 |
| s4 noon | 6.87 → **0.31** | 1.64 → 0.55 | 1.00 → 0.73 | 221.3 → 223.3 |
| s7 noon | 11.48 → **1.09** | 1.97 → 0.81 | 1.94 → 1.48 | 219.6 → 224.6 |
| s7 sunset | 23.12 → **5.89** | 2.96 → 1.41 | 3.33 → 2.66 | 175.4 → 189.0 |

- 噪点降 1–2 个数量级；平均亮度变化 ≤ 5 LSB（云没变薄/变暗）；
- 视觉核对（vision）：新版"奶油化/发糊"消除，无边带/块状/台阶；只剩轻微细颗粒；
- 成本：21 帧 capture 24 s → 114 s（**约 4.6×**，llvmpipe 1280×720）。

## 4. 剩下的真问题（要 Danis 拍）

1. **s7（积云+卷云双层）** 残余 5.9–8% 细颗粒 —— 细节层振幅 0.14 / 胞元 7 px 是"口味旋钮"；
2. **成本** 4.6×：要实时就得半分辨率 + 时域重投影，或把细节层挪到"表面"（每像素一次）；
3. 「足够细腻」的物理上限：一个像素装不下的细节**只能变成噪点**，不可能显示出来。
   所以正确目标不是"无限提高分辨率"，而是让**细节尺度跟着像素走**（本轮做法）。
   如果想在放大观察时仍然更细，唯一途径是真体积 + 更高步数/时域累积。

# 第七轮：性能（Danis：「这个 viewer 太卡了，能自己量下帧率优化下吗」）

## 1. 先量：`--bench-clouds <out_dir>`

新增 bench 入口（`jpov_skylight_viewer.cc::RunBenchClouds`），跑「关云 / s1 / s7」各 4 帧
（预热 1 帧后计时），打印 ms/帧。差值就是云的着色成本。

**1280×720 / llvmpipe / SMAA + 面板开（≈ 交互同配置）**：

| 场景 | ms/帧 | 说明 |
|---|---|---|
| 关云 | **89** | 固定开销：场景 + 面板 + SMAA + bench 自己的整帧 `glReadPixels` + PNG 编码（交互模式没有后两项，会更快） |
| s1（单层 32 步） | **400** | 云 ≈ 310 ms |
| s7（+高空卷云 12 步） | **474** | 云 ≈ 385 ms |

**进一步拆**（`BENCH_NO_ENV=1` 关环境探针 cube）：

| 场景 | ms/帧 |
|---|---|
| 关云 | 70 |
| s1 | 277 |
| s7 | 310 |

⇒ **环境探针 cube（128²×6 面，每帧重画）占 123–164 ms ≈ 全帧 30%**；主天空体积积分 ≈ 230 ms。

> ⚠️ **测法上的坑**：bench 里**第一个**被测的 scheme 会多付 ~3.2 s 一次性成本（首帧 shader
> 编译/JIT 落在计时窗口里），看起来像"关云比开云还慢"。只信**第二个及之后**的 scheme 数字。

## 2. 优化（两处，均为纯实现优化，观感不变）

### 2.1 把 8 个角点的浮点除法搬到入口（−30%）

`cloudHash3p` 每个角点都做 `p - period*floor(p/period)` ⇒ **每噪声调用 8×3 = 24 次浮点除法**，
一个密度采样 ~40 次噪声 ⇒ ~1000 次除法 —— 这是整条云管线最大的单点开销。
改成 `cloudNoise3p` 入口做**一次**取模折回 `[0,period)`，8 个角点只做整数比较折回（`cloudHash3c`）。

### 2.2 光程（自阴影）采样降档（−20%）

自阴影只需要"这条光程上有多少云"，不需要边缘的细碎形状：
- 形状 fbm 7 → **3** octave；
- **不做细节侵蚀**（4 octave / 32 次 hash）—— 它本来就是"细节"类工作；
- 不做像素锁定细节。

主步进仍是 5 octave + 侵蚀 + 像素细节。

### 2.3 顺带删掉无效成本

- 主步进 7 → 5 octave（实测 7 层与 5 层逐像素几乎一致，见第六轮）；
- 细节层 3 tap → 2 tap。

## 3. 结果

| | 优化前 | 优化后 | |
|---|---|---|---|
| s1 | 816 ms | **400 ms** | ×2.04 |
| s7 | 996 ms | **474 ms** | ×2.10 |
| `--capture-clouds` 21 帧 | 114 s | **51 s** | ×2.2 |

观感核对（同机位逐像素）：`|diff|` 均值 1.1–2.8 LSB、p99 7–20 LSB（主要来自自阴影不再带侵蚀细节），
噪点占比保持 0.4–6.6%（优化前 6.6–23.1%）。

## 4. 步数不能拿来换帧率（重要耦合）

LOD 用**像素足迹**做带限（第六轮），所以积分步长不参与带限 ⇒ 步数是**独立**的精度参数：

| 步数 | s1 ms | 噪点占比（s1 / s7 / s7 sunset） |
|---|---|---|
| 32 | 400 | 0.5% / 1.4% / 6.6% |
| 16 | 273 | **6.2% / 4.9% / 12.1%** |

⇒ 16 步时噪点立刻回到优化前的量级（积分欠采样）。**32 步是"无明显噪点"的下限**。

## 5. 还剩什么（要 Danis 拍）

1. **环境探针 cube 占 30%**：隔帧更新、或 128 → 64（反射粗糙度本来就走 mip 模糊，观感损失很小）。
   它在 `src/renderer.cc`，是所有 viewer 共用的路径，改它要连带看 env/水面 gold。
2. **真·实时**（60 fps）单靠 shader 优化到不了：需要**半分辨率云 + 时域累积**，或把体积云烘成 3D 纹理。
   当前 1280×720 单帧 ~2 fps，是 llvmpipe 软件光栅的下限附近的量级。
3. SMAA 在**无云平滑天空**上几乎不花时间（~20 ms 差值），云边缘密集时也 <10 ms —— 不是瓶颈。

# 第八轮：算力账单（Danis：「云的计算有多占算力？是每个像素都在积分光照？」）

## 1. 结论

- **不是每个像素**：地平线以下（`dir.y < 0.006`）直接返回；射线不与云板相交的不进循环；
  进入循环的像素在 `T < 0.02` 时提前退出。
- **光照不是"积分"**：自阴影是 **3 个固定光程点**（140 / 420 / 1100 m）各查一次密度，
  乘近似光程后取 `exp(-od)`。真正的步进只有主光路 32 步。
- **光照只占全帧 ~21%**：主成本是"每像素 × 32 步 × 3D 噪声查询"。

## 2. 每像素/每步的运算量（可数）

一次密度查询 = 8 角点 hash × octave 数：

| 项 | octave | hash 次 |
|---|---|---|
| 形状 fbm | 5 | 40 |
| 天气图 | 2 | 16 |
| 细节侵蚀 | 4 | 32 |
| 像素锁定细节 | 2 tap | 16 |
| **主步进合计** | | **≈ 104** |
| 光程采样（3 oct + 天气图）× 3 | 3+2 | 40 × 3 = 120 |

⇒ 单像素最坏 ≈ 32 × (104 + 120) ≈ **7200 次 hash**（约 14 万 ALU op）；
实际远低于此：空步只花 104、且命中云的像素通常十几步就 `T<0.02` 退出。

## 3. 实测占比（s7，1280×720，BENCH_NO_SMAA/NO_PANEL，取 3 次最小值）

全帧 **471 ms** = 固定开销 80 ms（场景/面板/SMAA/整帧回读+PNG） + **云 391 ms**。

各自**独立关闭**时的节省（同一台机器，三次取 min）：

| 关掉 | s7 | 全帧占比 |
|---|---|---|
| 3 个光程采样（自阴影 → 只剩环境项） | 471 → **372** | **−21%** |
| 像素锁定细节（2 tap） | 471 → **419** | −12% |
| 细节侵蚀（4 octave） | 471 → **446** | −6.5% |
| 环境探针 cube（128²×6 面/帧） | 474 → **310** | −35% |

⚠️ 这几项**不能相加**：探针 cube 跑的是同一套 shader，关掉任何一项也会连带省下探针里的那份。
换算到"云 391 ms"这个基数上：形状 fbm+天气图+步进循环 ≈ 一半，探针 ≈ 40%，
光程自阴影 ≈ 25%，像素细节 ≈ 15%，侵蚀 ≈ 8%。

## 4. 测法注意

- llvmpipe 的计时对负载很敏感（同一配置同机可见 ±20%），必须**多跑取 min**；
- bench 里**第一个** scheme 会多付 ~3 s（首帧 shader 编译），已把被测顺序改成 `{1, 7}` 规避。

# 第九轮：为什么这么贵 + 交互期自动降档（Danis：「3.2 fps 无法 debug」）

## 1. 为什么贵（可数的算术）

```
921,600 px（1280×720）
 × 32 步（主光路）
 × 1 次密度查询/步（命中云再加 3 次光程查询）
 × ≈104 次 hash/查询（8 角点 × [形状5 + 天气2 + 侵蚀4] + 细节2 tap）
 × ≈8 次浮点运算/hash
≈ 2.4×10^10 次运算/帧
```
llvmpipe 是 **CPU 软件光栅**（12 核 SIMD，实测量级 ~10^10 次/秒）⇒ 单帧 0.3–0.7 s。
这不是实现写得差，而是「每像素 32 次 3D 噪声」的固有成本；
再加上**环境探针 cube 把同一套 shader 又画 6 面**（+11% 像素，因每面固定开销实测占 35%）。

## 2. 加的东西：交互期自动降档

`CloudCommand::step_limit / fine_detail`（`interface/render_command.h`）+ 两个 uniform +
`SkylightApp::OneIteration` 里的判据：

```cpp
const bool interacting =
    input.left.IsHold()  || input.left.IsDrag()  || input.left.IsClick()  ||
    input.right.IsHold() || input.right.IsDrag() || input.right.IsClick() ||
    input.middle.IsHold()|| input.middle.IsDrag()|| input.middle.IsClick()||
    input.scroll_delta != 0.0f;
if (sky.cloud.enabled && interacting) {
    sky.cloud.step_limit  = kCloudDraftSteps;   // 8
    sky.cloud.fine_detail = false;
}
```

- **只认鼠标**：这个查看器的视角与面板都是鼠标操作（键盘没绑云相关操作）。
- **松手后的下一帧立刻回全质量** —— 不做时间收敛，避免"卡在草稿档回不去"的坑。
- headless 拍摄的 `InputSnapshot{}` 永远不是 interacting ⇒ **gold/截图逐字节不变**（已验：`s1/s7_noon` 与优化前完全相同，`loop_0/loop_6` md5 仍相同）。

## 3. 实测（同一进程内 baseline 相减，避免机器抖动）

| | s1 | s7 | 关云(baseline) |
|---|---|---|---|
| 全质量（32 步 + 细节） | 619 ms | **724 ms** | 132 ms |
| 交互草稿（8 步，无细节） | 307 ms | **322 ms** | 118 ms |

⇒ 云的开销 **592 → 204 ms（2.9×）**；按 Danis 实测 3.2 fps 换算，拖动时约 **8–10 fps**。

草稿档视觉核对（视觉模型）：云的**形态/云量/明暗与全质量完全对齐**，差别只是"细节与精度"
（有低步数的颗粒与色带，结构没变）⇒ 用来判断调参效果是够的。

## 4. 还能再快（都要 Danis 拍）

1. **环境探针隔帧更新 / 128→64**：占 35%，改 `src/renderer.cc` 共享路径（要连带复核 env/水面 gold）；

# 第十轮：地平线不自然 + 火烧云光感（Danis 2026-11-24 反馈）

## 1. 地平线"被刀切"的真正原因：不是云，是地平线本身

**实测**（`s7_sunset`，逐行平均亮度）：地平线处**一行之内**从 187 跳到 70（**Δ=100 LSB**）。
因为 `dir.y < 0` 直接取 `uGroundColor`，没有任何大气过渡 —— 云带是被这条硬边截断的。

**改法（只在 `uCloudOn != 0` 时启用 ⇒ 所有 sky gold 零回归）**：
- 新增 `horizon_haze`：取地平线方向（`dir.y=0.02`）的 Preetham 色，**去饱和**（长路径多次散射
  的观感就是"亮但不饱和"）；
- 地平线以上 3.4° 内把天空向霾色混合；地平线以下 1.7° 内把地色向霾色混合（渐变，不是跳变）。

**结果**：最大行间跳变 **100.2 → 2.8 LSB**（峰值 32.3，位置移到云内部，不再是地平线）。
副作用：正午天空平均亮度 −4.5 LSB（近地平线的霾带）。

**另一处形状修正**：凝结底不再是**绝对平面** —— 给底部 ±0.10 层厚（≈180 m）的低频起伏
（频率用 1.0、与风偏移同一整数周期 ⇒ 无缝循环不被破坏）。掠射时云底不再是一条完美直线。

## 2. 火烧云：三个根因 + 四条改动

**根因实测**：云的直射光只有**黑体色温**（7° 仰角 ≈ 3460 K，淡黄），没有"穿过大气"的颜色衰减；
环境项只占 4.5–10% 且取的是本方向天色（近地平线=橙）⇒ 受光面淡黄、暗部灰褐，没有冷暖对比。

| # | 改动 | 物理依据 |
|---|---|---|
| 1 | `cloudSunExtinction(lightDir)`：按大气质量 1/sin(elev) 做三通道衰减（7° ≈ (0.61,0.27,0.045)） | 低仰角光程长，蓝光被瑞利散射吃掉 |
| 2 | 环境项改为 **天顶色 ↔ 本方向色按高度混合**（云顶 80% 天顶色、云底 35%） | 云暗部由整个上半球照亮：夕阳时天顶深蓝 ⇒ 暗部发紫 |
| 3 | 多次散射**带颜色**：`mix(lightCol, amb_sky, 0.55)` | 云内多次弹射会把环境光混进来 |
| 4 | 宽前向散射瓣（只乘 `1-d`，只点亮薄处） | 逆光时薄云被背后太阳"透亮"，太阳周围暖光晕 |
| 5 | 大气透视 veil：`col = mix(col, bg, veil*0.75)`、`a *= mix(1,0.62,veil)` | 远云被大气散射洗淡并向天光色靠拢 |

**实测色彩**（`s7_sunset`，按亮度分位统计）：

| | 受光面 R/B | 暗部 R/B | 亮部亮度 |
|---|---|---|---|
| 改前 | 1.31 | 1.25 | 0.90 |
| 改后 | **2.05** | 1.34 | 0.80 |

即：受光面显著变暖（淡黄→橙），暗部保持相对偏冷，亮部不再过曝。
`loop_0/loop_6` 的 md5 仍相同（可平铺性未被破坏）。

## 3. 还差什么（诚实清单）

1. **饱和度**：照片的橙红更浓。要更接近得把**天空的色温曲线**也换成 airmass 模型；
   现在只对云做了（动全局会改所有 sky gold）。
2. **体积/层次**：AO `mix(0.55,1.12,1-d)` 太温和；近云厚、远云薄的层次还缺
   （应让消光/opacity 随距离变化）。
3. **形状重复**："棉花糖"感来自同一套 fbm；需要更强域扭曲或多尺度。
4. **色带**：天空渐变 + 8-bit 输出、无 dither；加 ±0.5 LSB 噪声即可消。
5. 照片下半部的水面倒影属于 water 场景，不在本 viewer。

# 第十一轮：airmass（大气质量）是什么 + 火烧云其实卡在一行 daylight 上

## 1. airmass 定义

光线穿过大气层的**路径长度**，以「从天顶垂直下来」为 1 的倍数：

```
AM(h) = 1 / sin(h)                    // 平面平行大气近似；h = 天体仰角
Kasten–Young: AM = 1 / (sin h + 0.50572 (h + 6.07995°)^(-1.6364))   // 含地球曲率/折射
```

| 仰角 h | 90° | 60° | 30° | 10° | 5° | 2° | 0° |
|---|---|---|---|---|---|---|---|
| AM | 1.0 | 1.15 | 2.0 | 5.8 | 11.5 | 28.7 | 38 |

透过率（Beer–Lambert，逐通道）：`T(λ) = exp(-τ(λ) · AM)`，τ 是三块之和：

- **Rayleigh（分子）**：∝ λ⁻⁴ ⇒ 蓝衰减最强（这是天蓝、日落红的根源）；
- **气溶胶/Mie**：∝ λ⁻¹~⁻¹·³，近似灰，强度由 turbidity 决定；
- **臭氧/水汽**：可选。

## 2. 我们代码里其实**已经**有三套 airmass 相关的东西（但不统一）

| 位置 | 现状 | 用在哪 |
|---|---|---|
| `sky_renderer.h::beerLambertAttenuation` | `AM = 1/max(sin,0.05)`，**标量** τ = 0.1+0.1·turbidity | 日月盘亮度 |
| `SkyCommand::SunDirectionalIntensity` + `DniFactorFromElevDeg` | 经验分段线性（非物理） | 物体方向光强度 |
| `sun_temp = mix(2000,5600, elev/0.3)`（shader）/ `SunDirectionalColor()`（CPU） | **经验色温映射**，与 AM/τ 无关 | 日月盘颜色、云直射光、物体受光颜色 |

所谓"换成 airmass 模型"= 把第三条删掉，改成 `T(λ)=exp(-τ(λ)·AM)` 的**逐通道**颜色衰减，
并让三处共用同一份 τ。**代码量小（两个函数、三处调用，约 40–70 行），但影响面大**：
日月盘、云的直射光、所有物体的方向光颜色都会变 ⇒ **6 张 sky gold 要重出 + 逐张肉眼复核**
（`standard_sunny_day`、`sun_path_0/1`、`sun_path_bloom_1`、`sun_path_nobloom_1`、`pick_highlight_sunny`）。

## 3. 但真正的瓶颈不是颜色，是一行 `daylight`

拍"太阳高度梯级"（同一机位只改仰角）发现：**太阳越低反而越灰、越没颜色**（反物理）：

| 仰角 | AM | 受光面 R/B | 亮部亮度 |
|---|---|---|---|
| 7° | 8.2 | 2.02 | 0.80 |
| 4° | 14.3 | 1.84 | 0.55 |
| 2° | 28.7 | 1.26 | 0.27 |
| 1° | 57.3 | 1.09 | 0.22 |

原因：

```glsl
float daylight = clamp((sun_y - 0.03) / 0.10, 0.0, 1.0);   // 老实现
```

从 sin(仰角)=0.03（≈1.7°）才开始、到 0.13（≈7.4°）才满 ⇒ **太阳在 2° 时只剩 5% 的日间光**，
天空与云被这条曲线直接压灰。真实黄昏里太阳贴地平线时天空仍然极亮（只是变红）。

**改成** `clamp(sun_y / 0.06, 0.0, 1.0)`（地平线起、3.4° 满）后：

| 仰角 | 修改前 受光面 R/B / 亮度 | 修改后 |
|---|---|---|
| 7° | 2.02 / 0.80 | 2.02 / 0.81（不变） |
| 4° | 1.84 / 0.55 | **2.22 / 0.76** |
| 2° | 1.26 / 0.27 | **2.11 / 0.59** |
| 1° | 1.09 / 0.22 | **1.78 / 0.43** |

⇒ 「火烧云」缺的那口气，主要不是颜色模型，而是**昼夜过渡把低太阳的日光掐掉了**。
`//tools/jpov/test/object3d/skydome:all` 4 个 gold 全绿（含 `sun_path` 黄昏）。

## 4. 结论 / 建议顺序

1. **先吃这一行**（已做）：低太阳变亮变红，零 gold 回归；
2. 再谈 airmass 颜色模型：收益是"浊度→红色的物理耦合"（高浊度更红更暗），代价是 6 张 gold
   重出 + 三处照明统一，需要 Danis 拍板；
3. 还有一个更便宜的观感项没做：**曝光**。真实夕阳照片是"对着天空曝光"，
   我们固定曝光 ⇒ 低太阳整体偏暗。加一个 ev 滑条/自动曝光，比改物理模型更直接。
