## 1. 渲染

### 1.1 CSM 阴影贴图过滤是 `GL_LINEAR` —— 与 acne/bias 耦合，暂不动
- **现象**：阴影里暗粒之间沿**光空间 texel 网格**出现「亮缝」（屏幕上随相机旋转）。
- **根因**：阴影贴图是 **RGBA32F 颜色纹理**（`.r` 存线性深度，当年为绕开 llvmpipe 下 depth 纹理采样不可靠）；「无遮挡」texel 存 clear 哨兵 **`1e16`**。过滤误设成 **`GL_LINEAR`**（`EnsureShadowFBO`，MIN+MAG）。PCF 本应按整数 texel 偏移逐 tap 采样，LINEAR 却把每个 tap 变成对 4 texel 的双线性插值 → 沾到 `1e16` 就判受光 → 亮从受光格渗出 ~1 texel。
- **旁证**：引擎其它 depth 纹理（`depth_tex_3d_` / `depth_tex_hdr_` / `scene_depth_tex_hdr_`）都是 `GL_NEAREST`，只有阴影这张是 LINEAR。
- **现状（2026-10-09）**：试改 MIN/MAG → `GL_NEAREST`（本地 commit `f2fb92e`，未 push）→ **Danis 在 sky light viewer 看到人体 body 露出 acne** → 判定「不敢妄动」→ **已回退，main 保持 `GL_LINEAR`**，本地分支已删。
- **🔑 关键认知**：`GL_LINEAR` 一直在**顺手扮演「阴影图模糊」**，把本来就有的 acne 糊掉了；去掉它就露出 acne + bias 不足。**所以「过滤」不是孤立 bug，它和 acne / bias 耦合** —— 要正确解决必须**连同 bias/acne 一起设计**，属单独一件事。
- **可能的修法（下次要动时的骨架）**：① 过滤/哨兵（NEAREST 或**有限哨兵**）；② 同时补 **bias**（自动几何偏置可能对掠射/自遮挡不够 → slope-scale bias / normal offset）。**二者一起调，别单独动。**
- **来源**：`memory/2026-10-09.md`。

### 1.3 远景（解析）雾边界锯齿 —— 像素叠加未考虑抗锯齿
- **现象**：远景解析雾（空气透视 / 仰角雾）在与几何、天空的**渲染边界**处存在**锯齿**。
- **根因（Danis 指）**：**像素叠加未考虑抗锯齿** —— 雾的合成按逐像素**硬边界**处理，没有按**覆盖率（coverage）**做亚像素加权。
- **现状**：未修。
- **可能的修法**：合成时引入覆盖率 / 亚像素权重（或对雾的边界区域做边缘抗锯齿），让雾边界与几何边缘一致。
- **来源**：Danis 2026-10-10 口述。

### 1.4 CSM 阴影 pass 不按级联剔除 —— 每帧 6 趟全场景几何（性能）
- **现象**：大场景（典型是植被实例：25 棵 oak 实例 ≈ 102 万顶点）在**软件光栅**（llvmpipe，
  WSLg/容器里常见）下交互只有 ~0.7 fps；且**每多一级联约 +1.1 s/帧**，与物体数量近似线性。
  实测（1280×720，容器 llvmpipe，6 帧总时长含 ~1.5 s 初始化；每档跑 3 次取中位数）：
  - 5×5 25 棵 + **5 级联（默认）**：9.4 s ⇒ ≈**1.4 s/帧**
  - 5×5 25 棵 + 1 级联：5.1 s ⇒ ≈0.6 s/帧
  - 3×3 9 棵 + 1 级联：3.9 s ⇒ ≈0.45 s/帧
  - 单株 + 5 级联：2.5 s ⇒ ≈0.15 s/帧
- **根因**：`Renderer::DrawShadowPass` 的循环结构是 `for (cascade) { for (cmd) 全量画 }` ——
  object3d / instanced_object / skinned **每一级都把整个场景重画一遍**，**不按
  `ShadowConfig::cascade_ranges[c]` 做距离剔除**。默认 `cascade_count = 5` ⇒
  主 pass + 5 级阴影 = **每帧 6 趟几何**（`kMaxCascades = 5`，见 `render_command.h`）。
  配合"每顶点沿关节链 texelFetch"的风 VS，顶点着色次数直接 ×6。
  次要放大器：叶卡双面 + alpha cutout 的 overdraw（实测关叶图几乎不降 ⇒ 不是主要矛盾）。
- **现状（2026-10-27）**：**引擎未改**。只在 vegetation v2 查看器加了规避旋钮
  `--shadow-cascades 1..5`（默认仍是 5）和 `--forest-grid`（降实例数）：
  `--shadow-cascades 1` 把 25 棵从 ~1.4 s/帧降到 ~0.6 s/帧，代价是阴影距离只有 8 m
  （2 级 24 m / 5 级 440 m）。另在 `JPOV::Init` 打了 GL 实现日志 —— 第一件要确认的事是
  "到底是不是 llvmpipe 在跑"（`GL: renderer=llvmpipe …`）。
- **可能的修法（按性价比排序）**：
  1. **按级联剔除**：每级只画与 `[cascade_ranges[c-1], cascade_ranges[c]]` 环带相交的物体。
     **前置工作**：命令上要有世界包围盒 —— `GltfObject` 有 `bounds_*`，但
     `InstancedObjectCommand` / `Object3DCommand` **只有摆放、没包围盒**，得先从 mesh 包围盒
     × 摆放推出（每帧一次，可缓存）。
  2. **交换双层循环**（每命令、级联在内层）：除剔除之外还能让 per-instance 数据每帧**只上传一次**
     （现状 6 次，见下"陷阱"）。
  3. **按平台自适应**：软件光栅统一降到 1~2 级、或降 shadow map 分辨率（`cascade_sizes`）。
- **⚠️ 陷阱（别踩）**：**不能"只在第一级级联上传实例数据"**。级联循环是「每级遍历所有命令」，
  同一块 `InstanceBuffer` 会被**下一条命令覆盖** ⇒ 在第 2 级跳过后就会画出别的命令的实例
  （树/道具整体错位）。要省必须换循环结构（见修法 2）或改参数纹理。
  同一条注释也写在 `UploadInstanceWindAttrs` 上方。
- **相关**：1.1（阴影过滤/bias 耦合）、7.3（条带不参与阴影生成）。三者都在
  "阴影 pass/CSM"这块，动其中一个要先想清楚另外两个。
- **来源**：2026-10-27 逐实例风 PR #237 的卡顿调查（Danis 报「25 棵 oak 交互很卡」）；
  细节见 `memory/2026-10-27.md` 16:37 那节。

## 3. 蒙皮 / 重定向

### 3.1 重定向（root-motion 尺度自适应）的已知残余
- **⚠️ 先澄清（别误读）**：重定向**已经处理** root offset ——
  `root_offset_t = Q_body · root_offset_s · (leg_t / leg_s)`，即 **朝向归一（`Q_body`）+ 尺度归一（腿长比）**，
  **2026-09-20 已落地**。骨长走目标 `SkeletonType` 自身长度；旋转经 rest 基准共轭 **100% 保留**（逐骨世界偏差精确一致）。
  **以上都不是残余。**
- **真正的已知残余**（`docs/jpov_root_offset_design.md` §4）：
  1. **标量腿长比是粗略近似** —— 更准应按「链长比」（根→脚 的骨长和之比）；步幅、接触点仍受影响。
  2. **接触密集动作需额外 IK 修正** —— scale adaptation 只对**模糊动作**（跑步/走路）够用，精确踩点（含**脚滑/悬空**）需 IK。
  3. **水平位移未做裁剪/居中** —— 大幅位移（跑步）角色会跑出画面（**预期行为**）。
  4. **沿链 `rest_offset` 差 → 微小脚入地/出地** —— 不处理（Danis 明确接受）。
- **来源**：`docs/jpov_root_offset_design.md` §4、`docs/jpov_retarget_design.md` §6.2/§6.3。

## 6. 测试 / 环境（不是引擎 bug，但会干扰开发）

### 6.1 JPOV 同进程二次 `Init()` 假失败
- **现象**：本机**无长驻 Xvfb** 时，`Finalize` 会杀掉自建 Xvfb 但**没 unset `DISPLAY`** → 同进程再次 `Init()` 假失败。
- **解法**：先起长驻 `Xvfb :99` + `DISPLAY=:99`。
- **来源**：`memory/2026-10-07.md`。

### 6.2 `Xvfb :99` 争用
- **现象**：自建 Xvfb 与测试内嵌 Xvfb 抢 `:99` → 大批 gold test **假 FAIL**（primitives2d / bone_mesh / pliers / text3d_depth_alpha）。
- **解法**：`pkill Xvfb :99` 释放，或起长驻 `Xvfb :99` + `--test_env=DISPLAY=:99`。⚠️ `pkill -f "Xvfb :99"` 会**自匹配到自己的命令行**，小心。
- **附**：多个 session 并发跑测试（不同 `ai_infra_*`）各自 bazel `output_base` 隔离、互不影响编译，但**都抢 :99**。
- **来源**：`memory/2026-10-09.md`。

## 7. 半透明条带（Strip3D）

> 采样数四档（4/8/16/32）落地后（PR #229，2026-10-26 合入），条带的**功能面**基本齐了；
> 下面这些是**有意推迟 / 还没量**的部分，都不是 bug。

### 7.1 条带消费的 CSM 没有 PCF 软化 —— 阴影过渡突兀
- **现象**：玻璃缸场景里，树投在缸壁上的阴影边缘是**软块状硬边**（不像 object3d 那边有黄金角软化）。
- **根因**：§19.15 的取舍 —— 单级联单次采样、无 PCF（`CsmTap` 每片元只比一次），理由是
  「条带是薄片、片元多」「shadow map 是给不透明几何生成的」。这个理由对**物理精度**成立，
  对**观感**不成立；fire_fog 同样单次采样但雾本身软、看不出来，所以只有锐利的条带暴露。
- **现状**：**未修**，记在 GitHub issue **#226**（`fix(jpov/strip): 条带消费 CSM 缺黄金角(PCF)软化`）。
- **可能的修法**：复用 `ShadowPcfConfig::GoldenSpiralOffsets()` + object3d 的 `pcfShadow()`
  （12 tap / 半径 2 纹素），把 `shadow_pcf` 塞进 `StripCsmShadow`；**偏置要乘采样核有效半径**
  （否则 12 tap 各自偏置不足 → 斜面 acne）；保持「不开天光零成本」。
- **来源**：GitHub issue #226、`docs/jpov_strip3d_translucent_design.md` §19.15、2026-10-25 Danis 口述。

### 7.2 条带不采环境镜面 —— 反射色是常量
- **现象**：玻璃/薄膜的边反只会朝 `rim_color` 这个**常量色**靠，映不出天空、树、地面。
- **根因**：`StripFresnel::rim_color` 是写死的颜色；条带 FS 里**没有任何 env cubemap 采样**。
  #228 的环境镜面（IBL specular）只注入 PBR（object3d / instanced / skeleton）三份着色器，条带不在内。
- **现状**：未做（`docs/.../jpov_strip3d_translucent_design.md` §19.6 已列为已知限制）。
- **可能的修法**：把 #228 的 `SkyRenderer::DrawSkyEnvCube` 探针纹理按 **17 号单元**喂给条带 FS，
  在 `SkyLightRadiance` 之外再加一项「粗糙度近似反射」（条带没有 roughness，需要按 fresnel 的
  `power` 反推一个 mip 级别，或直接固定取 1~2 级）。
  ⚠️ 注意：真要做「水面/海洋」，这条路不够 —— 需要**平面反射 / SSR**。
- **来源**：PR #228、§19.6、2026-10-26 本轮 review。

### 7.3 条带不参与阴影生成（不写 shadow map）
- **现象**：玻璃/薄膜不会给后面的物体投影。
- **根因**：半透明片要写 shadow map 得单开一次 shadow pass（或 alpha-tested 变体），
  和「条带只是一个 effect pass」的定位冲突。
- **现状**：**Danis 明确先不搞**（2026-10-25 定）。
- **可能的修法**：真要做得给条带单独一个 `shadow_cutout` 变体 + 独立 depth FBO，
  按 α 阈值写深度；收益/代价要先量（见 7.5）。
- **来源**：§19.15 末尾、Danis 2026-10-25 口述。

### 7.4 UV 只能铺一遍 —— 沿长度不能平铺
- **现象**：条带纹理沿长度**正好铺一次**；做不出雨丝、标线虚线、重复布纹这类「周期性图案」。
- **根因**：顶点属性里的 `u = col / (samples−1)` 恒在 `[0,1]`；`TextureManager` 虽然有
  `repeat` 选项（`WRAP_REPEAT`），但条带拿不到 >1 的 u，所以 repeat 起不到作用。
- **现状**：未做。**这条正好卡住 4 点档最典型的用途**（雨丝/辅助线/道路标线）。
- **可能的修法**：批级或 per-strip 加一个 `tex_repeat`（沿长度平铺次数），FS 里
  `ModulateTexture(vec2(vUV.x * repeat, vUV.y))`；per-strip 就塞进 per-instance 数据纹理
  现有的空闲位（行宽 = samples + 9，9 个 knot 之后还有 3 个通道没用）。
- **来源**：2026-10-26 本轮 review（Danis 问「strip 还差啥」）。

### 7.5 四档没有 frame-time 基准 —— 「该选哪档」目前只能靠结构推断
- **现象**：没有任何一次条带性能测量（4/8/16/32 × 折线/平滑 × 天光开关）。
- **根因**：gold 渲染里 PBR/CSM/bloom 占大头，测不出条带本身的成本，所以一直没做
  （§19.12、§20 都写了「不编数字」）。
- **现状**：未做。**已知的结构性结论**：四档**片元成本相同**（同一份 FS，覆盖像素一样多），
  差别只在顶点/索引量（8/16/32/64 顶点）与顶点着色。
- **可能的修法**：一个独立 bench demo（固定机位、N 条带、无后处理），输出 CPU 展开+上传 与
  GPU pass 的毫秒数；四档 × 两插值 × 天光开/关 = 16 组。
- **来源**：§19.12、§20、2026-10-26 本轮 review。

### 7.6 gold 覆盖不对称：只有 16 点有 gold
- **现象**：4 / 8 / 32 三档**没有独立 gold**，画面只靠 viewer capture 人眼验收；
  另有 `strip_degenerate_test`（退化几何）覆盖它们「不崩、不污染」。
- **根因**：四档化是最后一步，先保证 16 点档行为逐位不变（10 张 gold），新档位的金图没补。
- **现状**：未做。
- **可能的修法**：每档一张固定构图 gold（同一相机/材质，只换档位），断言彼此「差异像素数落在
  区间内」（4 点最折线、32 点最平滑），而不是互相逐像素比。
- **来源**：PR #229、2026-10-26 本轮 review。

### 7.7 折线 pass 没有解析 AA（只有平滑 pass 有）
- **现象**：细条带在 `kPolyline` 下边缘更硬；平滑 pass 有 `fwidth` 裁形 AA，折线 pass 没有。
- **根因**：折线 pass 的轮廓直接来自顶点插值，没有「真实参数 vs 保守外扩」这一步，
  所以也没有可用来做 1px 覆盖度的 `v*`。目前靠**宽度剖面**（profile 两端收到 0）+ 后处理 SMAA。
- **现状**：有意为之（折线 pass 的定位就是「快、够用」）。
- **可能的修法**：给折线 pass 也加 `fwidth(vUV.y)` 的边缘覆盖度（代价：每片元多一次导数推导，
  把「折线＝更便宜」这条优势削掉一部分）。要做先量（见 7.5）。
- **来源**：§18.5、2026-10-26 本轮 review。

### 7.8 一个 batch 只能一个混合集合
- **现象**：「膜 + 加法高光」这种组合要发**两个** batch（两次 draw call）。
- **根因**：`StripBlend` 是批级字段，`kCoverage` / `kEmissive` 互斥（WBO 两套附件的语义不同）。
- **现状**：未做（§19.6 已列）。
- **可能的修法**：一条命令同时写两个集合（需要一个「混合模式」枚举 + FS 里两段写入），
  或者干脆接受两次 draw call（当前做法，成本可控）。
- **来源**：§19.6。
